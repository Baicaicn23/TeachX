### 2.2 消融实验：同义词查询扩写贡献了多少

这是**本作品最有说服力的一条证据**——因为"双基线对照"通常只能给出前后两个数，
而这里可以**当场切换单个变量**，把增益归因到具体机制。

评测 CLI 暴露了 `--no-expand` 开关（`evals/run_rag_eval.py:230`），关闭同义词扩写：

```bash
cd backend
# 关闭查询扩写，其余配置不变
uv run python -m teachx.evals.run_rag_eval --no-expand
uv run python -m teachx.evals.run_rag_eval \
  --dataset evals/datasets/rag_retrieval_semantic.json --no-expand
```

实际输出（2026-10-08 实测）：

| 卷 | 配置 | Hit@3 | Recall@3 | MRR |
| --- | --- | ---: | ---: | ---: |
| 关键词卷 | 关闭扩写 | 1.000 | 1.000 | 0.938 |
| 关键词卷 | **开启扩写** | 1.000 | 1.000 | 0.938 |
| 语义改写卷 | 关闭扩写 | **0.500** | **0.500** | **0.417** |
| 语义改写卷 | **开启扩写** | **1.000** | **1.000** | **1.000** |

**结论**：同义词查询扩写对**关键词卷零影响**（该卷查询本就使用术语，FTS 直接命中），
对**语义改写卷是决定性的**——Hit@3 从 0.500 提升到 1.000，MRR 从 0.417 提升到 1.000。
6 条口语化查询中有 3 条在关闭扩写时完全召回失败。

**这条证据解释了为什么需要"双卷"评测**：单看关键词卷会得出"查询扩写没用"的错误
结论，只有引入口语化改写卷才能暴露机制的真实价值。这是评测设计本身的贡献。

### 2.3 P2 优化全过程（记录）

| 阶段 | 关键词卷 MRR | 语义卷 MRR |
| --- | ---: | ---: |
| 优化前（FTS5 默认 unicode61 分词器，无扩写） | 0.688 | 0.639 |
| 优化后（trigram 重建迁移 + 同义词扩写 + 跨库回退） | **0.938** | **1.000** |

根因：FTS5 默认 `unicode61` 分词器不切分中文（整段中文视为一个 token，`MATCH`
中文词零命中），中文检索此前依赖 `LIKE` 兜底 + 向量通道。改为 `trigram` 后
FTS 通道才真正生效。

> §2.3 的"优化前"数值来自开发过程记录，**其配置已被覆盖**，不能直接复跑得到；
> 可复跑的是 §2.2 的消融实验。材料中引用时应说明这一区别——这正是"如实区分
> 已完成与过程记录"的例子。

## 五、稳定性机制对照表

| 机制 | 解决什么问题 | 代码位置 | 关键配置 |
| --- | --- | --- | --- |
| 有限退避重试 | 模型端点瞬时失败、限流 | `runtime/tools.py` `ToolRegistry.execute()` | `tool_max_attempts=3`，退避 200ms → 2000ms |
| 幂等去重 | 工具重复调用不产生副作用 | `runtime/tool_executions.py` | 幂等键 = user+session+turn+call+tool+参数指纹；唯一约束防并发重复 |
| 敏感参数脱敏 | 隐私字段不进事件与持久化记录 | `runtime/tools.py:54,470` | `sensitive_arguments` 声明的字段值替换为 `***` |
| 有界并发 | 只读工具并行、副作用工具串行 | `runtime/engine.py` | `tool_max_concurrency=4`，设为 1 即完全串行 |
| 整回合超时 | 上游无响应时不悬挂 | `runtime/engine.py` | `turn_timeout_seconds=300`，三个检查点 + 流看门狗 |

**错误语义分层**（材料可讲的设计取舍）：

- `ToolError` = 永久失败，**不重试**
- `ToolTransientError` = 临时失败，**重试**
- `ToolTimeoutError` = 单次执行超时
- 未知异常默认按永久失败处理（保守，避免无意义重试放大费用）

## 六、失败归因：trace 五层

```bash
cd backend
uv run python -m teachx.runtime.turn_trace --session <会话id>
```

责任层定义在 `runtime/turn_trace.py:21-25`：

| 层 | 归因对象 | 典型错误码 |
| --- | --- | --- |
| 模型层 | 模型输出问题 | `output_truncated` |
| 检索层 | 知识库召回问题 | 空检索 |
| 工具层 | 工具执行问题 | 工具失败、重试耗尽 |
| 编排层 | Agent Loop 问题 | `max_rounds_exceeded`、`turn_timeout` |
| 费用层 | 预算问题 | 预算超限 |

**真实案例（可写进答辩）**：在做端到端评测时发现，推理型模型会把全部输出预算花在
思考上、返回空内容却报告 `completed`——即**空回答伪装成成功**。归因到模型层后，
新增了第四个诚实失败码 `output_truncated`（`finish_reason="length"` 且无可见内容
→ `failed` + `retryable`），并配套单元测试。

这个案例的价值在于：**评测的产出不是分数，而是发现了产品缺陷**。这是"把质量当作
可测量对象"主张的具体证据。
