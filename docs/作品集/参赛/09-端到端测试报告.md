# 端到端测试报告 · 2026-10-08

> **测试目的**：在真实运行环境（真实 DeepSeek 模型 + 真实前后端）下，用一个
> 真实学生情景走通产品主流程，找出「材料声称已完成、实际不可用」的功能。
>
> **为什么这份报告重要**：竞赛评分标准要求"材料与实际成果一致"。本报告发现了
> **2 个高严重度缺陷**，其中 1 个直接推翻材料里的"已完成"声明。

---

## 一、测试方法

| 项 | 设置 |
| --- | --- |
| 环境 | 本地 `./scripts/dev.sh`（后端 8010 / 前端 3000） |
| 模型 | 真实 DeepSeek `deepseek-flash`（`.env` 配置） |
| 数据库 | `data/teachx.db`，五个学科知识库（26 份文档），**无用户** |
| 登录 | 脚本注册账号 `student_e2e`（首个用户 → 管理员） |

| 轮次 | 14 轮（含两轮完整重跑）+ 3 轮最小复现 + 1 轮探针 |

### 情景设定

> **人物**：大二学生，期末周，同时准备三门——高等数学（微积分）、大学英语四级作文、
> 大学物理。前两门有资料，**大学物理完全没有资料**（知识库里没有这个库）。
> 这个设定是刻意的：它同时测试"有资料时答得准"和"没资料时是否诚实"。

### 测试脚本所走的路径

```text
A 会话（高数）：问概念 → 要求计算 → 要求学生把题目沉淀进库
B 会话（四级）：问资料 → 要求围绕知识库出练习题
C 会话（物理）：问一个知识库里完全没有的主题
D 会话（记忆）：显式要求"记住：…"
E 会话（新会话）：问"规划复习"，验证跨会话记忆是否生效
```

## 二之二、修复与验证（同日完成）

### P1 修复：放宽输出上限

`.env` 增加一行（**不改代码**——默认值 1024 是有意的成本控制，只在本机演示环境放宽）：

```text
TEACHX_MAX_OUTPUT_TOKENS=4096
```

**验证证据**：修复后重跑同一情景，`llm_usage` 出现 `completion_tokens = 1051`
（**超过旧的 1024 上限**，证明配置确实生效）；此前反复变空的提问
（"我明天考高数，帮我讲讲定积分和不定积分有什么区别？"）现在稳定产出 413 字回答。

### P2 修复：补传 `is_admin`

`runtime/tools.py` 的 `SaveToKnowledgeBaseTool.execute` 补上漏传的参数：

```python
result = await self.service.add_document(
    knowledge_base,
    f"{title}.md",
    dated.encode("utf-8"),
    owner_id=owner_id,
    is_admin=context.is_admin if context else False,   # ← 新增
)
```

**配套测试**（`tests/test_save_to_kb.py`，新增 2 条互为边界的用例）：

| 用例 | 断言 |
| --- | --- |
| `test_admin_can_save_into_global_kb` | 管理员往全局库（owner_id 为空）沉淀**成功** |
| `test_non_admin_cannot_write_into_global_kb` | 普通用户往全局库沉淀**仍被拒** |

第二条是必须的——**修复不能把安全守卫一起修掉**。同一个 `ensure_base` 守卫，
对管理员放行、对普通用户保持拦截。

**验证证据**：

1. **测试确实是回归守卫**——把修复临时撤掉，`test_admin_can_save_into_global_kb`
   立刻变红，报出与生产完全一致的错误
   `KnowledgeError: 知识库已存在：高等数学-微积分`；恢复修复后全绿。
2. **真实环境端到端通过**——重跑情景，学生说"把这道题存进高等数学-微积分"，
   模型回复"**已存好 ✅ 知识库「高等数学-微积分」→《定积分计算：∫₀²(3x²+2x)dx》**"，
   工具调用 1 次、状态 `completed`。
3. **全量检查**：`./scripts/check.sh` → `All checks passed!` + **173 passed**
   （修复前 171，新增 2 条；此后新增「从错题出题」等功能，全量当前为
   184 passed，见 [03-评测证据包](03-评测证据包.md)）。

## 三、缺陷详情

### P1 🔴 输出上限 1024 → 整轮回答为空

**现象**：全库 23 条用户提问，只有 21 条有回复。缺失的 2 轮，学生提问后**没有任何回应**。

**证据**（`llm_usage` 表，50 次调用中的 5 次撞顶）：

| 调用 id | 会话 | completion_tokens | 其中 reasoning | 该会话消息 |
| ---: | --- | ---: | ---: | --- |
| **2** | 高数（第 1 次跑） | **1024** | **1024** | 用户 3 条，助手 2 条 ← **缺 1 条** |
| **18** | 高数（第 2 次跑） | **1024** | **1024** | 用户 3 条，助手 2 条 ← **缺 1 条** |
| 13 | 物理 | 1024 | 890 | 用户 1，助手 1（有回复） |
| 33 | 矩阵的秩 | 1024 | 835 | 用户 1，助手 1（有回复） |
| 35 | 高数 | 1024 | 904 | 用户 1，助手 1（有回复） |

**根因**：`deepseek-flash` 是**推理型模型**，输出预算先被"思考"消耗。
当 `completion_tokens == 1024 == TEACHX_MAX_OUTPUT_TOKENS` 且 `reasoning_tokens`
也占满 1024 时，**可见内容为 0**。系统按诚实失败契约判定为失败、不写入空的
助手消息——所以学生端是**彻底的空白**，连错误提示都没有。

**这不是新问题**：交接文档已记录"推理型模型会把输出预算花在思考上，默认 1024
可能截断到空回答，联调建议 4096"。但 `.env` **没有覆盖这个默认值**，所以它一直在生效。

**影响**：对一个要现场演示的产品，**第一句话就有一成概率（5/50 撞顶，其中 2 次全空）
返回空白**。这是演示级灾难。

**建议**：`.env` 增加一行即可，无需改代码。

```text
TEACHX_MAX_OUTPUT_TOKENS=4096
```

**验收方式**：重跑本报告 §一的情景，确认 23/23 轮全部有回复。

---

### P2 🔴 `save_to_knowledge_base` 在演示配置下必然失败

**现象**：学生说"把这道题存进高等数学-微积分"，工具**连续两次**返回
「知识库已存在：高等数学-微积分」，写入失败。模型如实告知用户"没存进去，
我不能假装它已经在了"——**诚实失败契约生效了，但功能本身是坏的**。

**根因**（已定位到具体行）：

`runtime/tools.py:344` 调用时**漏传了 `is_admin`**：

```python
result = await self.service.add_document(
    knowledge_base, f"{title}.md", dated.encode("utf-8"), owner_id=owner_id
)   # ← 没有 is_admin=context.is_admin
```

而 `ToolContext` **是有 `is_admin` 字段的**（`runtime/tools.py:88`），
`add_document` 也**支持这个参数**（`knowledge/service.py:189`）。只是没传。

于是 `ensure_base`（`knowledge/service.py:110-122`）的逻辑走到：

```text
get_base(库名, owner_id=当前用户, is_admin=False)   → None
  （因为库里那份资料的 owner_id 是空 = 全局库）
→ 进入 if owner_id and not is_admin 分支
→ get_base(库名, is_admin=True) → 找到了
→ raise KnowledgeError("知识库已存在：…")        ← 这里炸的
```

这段守卫的**本意**是"防止普通用户往别人的同名库里写"，但因为
`is_admin` 没传进来，**管理员自己也被拦住了**。

**为什么这个 bug 特别危险**：种子演示数据里**五个知识库的 owner_id 全是空**
（即全局库），而演示账号是首个注册用户 = 管理员。也就是说
**"管理员往全局库沉淀"这条路径 100% 失败**——恰好就是演示路径。

**影响**：参赛材料 [01-作品说明](01-作品说明.md) §三把"随手沉淀"列为核心功能，
§十一把"学科知识库沉淀"列入**已完成**。**这两处在修复前是不成立的。**

**建议修复**（一行）：

```python
result = await self.service.add_document(
    knowledge_base, f"{title}.md", dated.encode("utf-8"),
    owner_id=owner_id, is_admin=context.is_admin if context else False,
)
```

配套加一条测试：管理员往全局库（owner_id 为空）沉淀应当成功，且**普通用户
往他人同名库沉淀仍应被拒**（守住原来的安全语义，不能修掉守卫）。

### P3 🟡 检索类问题被判成闲聊

**现象**：学生选了"大学英语四级"库，问"**四级作文有哪些万能句型？**"
→ 判定为 `smalltalk`（闲聊），路由到 `chat` 子 agent，**没有调用检索、
没有返回任何引用**。两次完整重跑**都判错**。

**为什么值得注意**：意图考卷是 **38 条样本、准确率 1.000**，但它没覆盖住这句
最自然的真实问法。这是"评测集覆盖不足"的实证——**考卷全绿不等于真实场景不出错**。

**影响**：用户明确选了知识库提问资料类问题，却得不到基于资料的回答和引用，
会直接怀疑"它到底有没有看我的资料"。

**建议**：把这类真实问法补进 `evals/datasets/intent_classification.json`
（至少 5 条"XX有哪些/是谁/是什么"的资料型问法），再看规则层是否需要加
"有哪些"这类信号词。**先补考卷让它变红，再修**。

### P4 🟡 讲解子 agent 不检索，也不告知"库里没有"

**现象**：学生问"**大学物理里的熵增定律怎么理解？**"（知识库里**没有**大学物理）
→ 判定 `concept_explain`（置信度 0.97）→ 路由到 `tutor` →
**工具调用数 = 0**，完全没调用 `knowledge_search`。

结果：模型用自己的通识讲了一整套熵增，学生**无从知道这不是基于资料**，
也**没有任何提示说"你的资料库里没有这部分"**。

**为什么是问题**：产品对用户的承诺是"**知识库里没有的东西它会直说**"
（见 [使用指南](../../使用指南.md)）。但这里的实际情况是**它压根没去查**，
所以无所谓"说不说"。

**根因方向**：`tutor` 的默认工具里**是包含** `knowledge_search` 的
（`runtime/intents.py` 的 `AGENT_PROFILES`），模型自己选择不调用。
属于**提示词层面的引导不足**，不是权限或代码缺陷。

**建议**：在 `tutor` 的角色提示词里补一条——涉及知识性提问时**先检索**，
检索为空时明确告知用户"资料库里没有相关内容，以下是通用讲解"。这样
"诚实"才落得到实处。改完需要跑一遍任务级考卷确认无回归。

---

### P5 🟡 闲聊里的"出题"拿不到知识库

**现象**：学生说"**围绕我的知识库出 3 道四级作文练习题**"→ 路由到 `practice`
子 agent（路由正确）→ 但它回答"**我这边看不到你的知识库**"，
最后出的是**通用的四级作文题**，不是围绕学生资料生成的。

**根因**：`practice` 子 agent 的设计是 `denied_tools=("knowledge_search",)`
——**故意禁止检索**（教学意图：做题时别让学生去资料里找答案）。

**这是一个真实的设计张力**：禁止检索的**教学理由成立**（防止用资料代替回忆），
但"**基于学生资料出题**"这件事本身**需要读到资料**。两者的冲突导致
聊天里的出题名不副实。

**注意**：`/practice` 页面走的是另一条通路（`PracticeService` 直接从
知识库片段生成题目，见 `practice/service.py`），**那条是好的**。
问题只在"聊天里让 AI 出题"这一条路径上。

**建议**（三选一，需要产品决策）：
1. **推荐**——让 practice agent 可以读知识库**用于出题**，但约束它
   **不把原文直接给到回答里**（用提示词约束，而不是禁止工具）；
2. 承认边界：在提示词里明确"聊天出题是通用出题，要基于资料请到 /practice 页面"；
3. 维持现状，但在参赛材料的"已知边界"里如实写出来。
