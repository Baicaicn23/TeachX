## 每次迭代怎么执行

每个大型功能都遵循同一套流程：

```text
明确用户场景
→ 定义本次范围和明确不做的内容
→ 设计接口与数据流
→ 先实现后端核心
→ 接前端页面
→ 补自动测试
→ 浏览器端到端验证
→ 补中文教程
→ 大功能更新 README
→ commit
→ push
→ 更新本路线图
```

每次任务结束前都要做一次文档判定，写作标准见
[TeachX 文档写作指南](../规范/文档写作指南.md)。新功能必须补适合基础读者的中文教程；
纯重构或测试调整可以不新增教程，但要检查现有说明是否已经不准确。
大型功能教程还必须包含至少 8 个面试问答，解释为什么这样设计、替代方案、失败模式和
工程取舍，方便把项目经历讲清楚。

### 一个里程碑的完成标准

只有同时满足以下条件，才算“完成”：

- 用户可以在浏览器实际操作。
- 后端有真实业务逻辑，不是静态 Mock 页面。
- 至少有一个正常路径测试和一个失败路径测试。
- 前端类型检查通过。
- 后端测试通过。
- 文档说明当前能做什么、不能做什么。
- 代码已提交并推送到 GitHub。

### P0：意图识别 + 多 Agent 路由（先做）

- 意图枚举收敛到教学场景：`concept_explain`（概念讲解）/ `practice`（做题练习）/
  `progress`（查进度）/ `retrieval`（资料检索）/ `calculation`（计算）/ `smalltalk`。
- 识别：规则关键词兜底 + LLM 结构化 JSON 输出（`{"intent": "...", "confidence": ...}`），
  走 provider.complete 低 token 调用；解析失败回退规则结果。
- 路由：意图 → 子 agent 配置表（专属系统提示词 + 工具子集）。
  讲解 agent=知识检索+计算；练习 agent=练习工具（**不给检索**，工具最小权限）；
  进度 agent=只读档案；未识别/闲聊=默认 chat。
- 实现：AgentRuntime 前置意图路由层（纯函数 + 一次可选 LLM 调用），
  `tool_call`/`done` 事件带 `intent` 字段。
- 验收：标注意图评测集（≥30 条）准确率 ≥90%；每个意图路由到正确子 agent；
  意图评测进 check 流程（Mock/规则可跑）。

### P1：端到端 Agent 评测

- 任务级评测集：`{任务输入, 期望行为断言}`——必调工具、回答必含要点、
  禁止行为（如练习意图不得检索）。
- 两层执行：Mock 全链路确定性断言（回归门禁，进 check）；真实模型小样本
  LLM-as-a-Judge（忠实度/有用性 1~5 分，≤20 题，用智谱 Key）。
- 失败自动调 `turn_trace` 归因到五层——把 E6a/E6b/E6c 串成闭环。

### P2：检索召回优化（每步量化）

查询改写（同义词表 → LLM 改写）→ 召回参数调优（每路召回数/RRF k）→
空结果回退策略（提示换说法/扩大范围/降级闲聊）。**每一步用语义考卷
（rag_retrieval_semantic.json）量化 RR/Hit 变化**，退化被基线门禁拦截。

### P3：跨会话长期记忆 + 在线监控聚合

- 长期记忆：会话结束抽取“关于用户的长期事实”（学习版可规则化 + 可选 LLM），
  存 memory 表；下会话检索注入系统提示词；记忆可列举/删除（不越权）。
- 在线监控：聚合接口或 CLI（回合数/失败率/工具失败率/空检索率/时延 P50/P95），
  数据源 = 持久化事件 + llm_usage + turn_trace。

## Git 记录规范

每个大型功能至少拆成两类提交：

```text
feat: 功能代码、测试、迁移
docs: 对应教程、README、路线图
```

提交后必须推送：

```bash
git push
```

然后更新本文件的：

1. 当前状态。
2. 当前 Git 基线。
3. 新的已完成里程碑。
4. 下一个当前开发阶段。

## 教程和路线图的区别

- `docs/规划/开发路线图.md`（本文件）：记录“项目做到哪里，下一步做什么”。
- `docs/tutorials/`：解释“为什么这样做，代码怎样运行”。
- `README.md`：给第一次访问项目的人展示“项目是什么，现在能做什么”。
- `docs/参考/架构与数据流.md`：解释稳定的系统结构和设计规则。

任何一个文件都不应该重复承载全部信息。
