## E1、E2 已完成：不要重做

### E1：工具执行政策与重试（进入 `502bbcd`）

- 工具用 `ToolPolicy` 声明只读、最大尝试、超时和退避；`None` 继承默认值。
- 错误分类：`ToolError` 永久不重试；`ToolTransientError` 临时可重试；
  `ToolTimeoutError` 超时可重试。SQLite locked 自动转为临时错误。
- `tool_result` 事件携带 `attempt_count`、`retry_count`、`retry_delays_ms`、
  `duration_ms`、`error_code`、`retryable`、`timed_out`。
- 测试：`backend/tests/test_tool_reliability.py`；教程 19 有 15 个面试问答。

### E2：工具执行幂等保护（进入 `cfaab58`）

- 幂等键 = SHA-256(user_id|session_id|turn_id|call_id|tool_name|参数指纹)，
  参数只存 hash 不存原文，跨用户不共享记录。
- `tool_executions` 表唯一约束 + 原子插入实现并发控制；completed 重放、
  永久失败重放、可重试失败接管、stale running 可接管。
- `tool_result` 事件新增 `deduplicated`、`replayed`、`execution_status`、
  `idempotency_key_hash`。
- 测试：`backend/tests/test_tool_idempotency.py`（10 个）。
- 设计细节和真实验证记录见教程 19 第 11～12 章和第 16～23 题面试问答。

### E3：敏感工具参数脱敏（进入 `f8f7dd2`）

- 工具用 `ToolPolicy.sensitive_arguments=("api_key", ...)` 声明敏感参数名。
- `tool_call` 事件的参数和结果 metadata 的同名字段统一打码为 `***`；
  发给模型的原始参数和工具收到的参数不打码；幂等键仍用原始参数 hash。
- 配置 `TEACHX_TOOL_REDACTION_ENABLED=true`（默认开）。
- 测试：`backend/tests/test_tool_redaction.py`（7 个）。
- 设计细节、边界（结果正文不自动打码）和验证记录见教程 19 第 13～14 章和
  第 24～28 题面试问答。

### E4：多工具执行策略（进入 `8c870d3`）

- 模型一轮返回多个调用时，连续只读调用组成一批，经 `asyncio.Semaphore`
  限流的 `asyncio.gather` 并发执行；有副作用/未知调用单独串行。
- `gather` 保序：`tool_result` 事件和发给模型的 `tool` 消息严格按模型调用顺序。
- `tool_call` 事件新增 `batch_size` 和 `parallel` 字段。
- `ToolRegistry.is_read_only(name)` 是查询接缝；未知工具按有副作用处理。
- 配置 `TEACHX_TOOL_MAX_CONCURRENCY=4`（设为 1 即完全串行，可当回滚开关）。
- 测试：`backend/tests/test_tool_concurrency.py`（7 个，用峰值计数器证明并发）。
- 设计细节和组合验证见教程 20。

### E5：整回合超时与断线恢复提示（进入 `8ccb596`）

- 整回合时间预算 `TEACHX_TURN_TIMEOUT_SECONDS=300`（0 关闭）；三个检查点：
  每轮开始、流式片段之间（每片一个 `wait_for` 看门狗，`StopAsyncIteration`
  先转哨兵值再过 Task）、每批工具执行前（剩余预算包住批次，超时取消）。
- 统一错误码：`turn_timeout`、`max_rounds_exceeded`、`stream_interrupted`
  （由 `provider_stream_error` 更名），均 `retryable=true` + `turn_terminal=true`。
- max_rounds 耗尽不再发罐头文本伪装回答：无内容 → error + done failed、
  不保存假回答；有部分内容 → 保存助手消息并标记 `partial=true`，
  done 为 `failed + partial`。
- 前端无需新组件：已有的终端错误展示和 `retryable` 驱动的重试/重新生成
  机制直接消费新契约。
- 测试：`backend/tests/test_turn_boundaries.py`（6 个）。
- 设计细节和真实验证事件流见教程 21。

### E6a：RAG 检索评测（进入 `0bbeb7f`）

- 固定评测集 `backend/evals/datasets/rag_retrieval.json`：5 篇线性代数语料 +
  8 个查询，gold 用关键句子串标注（对切块变化免疫）。
- 指标 `backend/src/teachx/evals/metrics.py`：Hit@K / Recall@K / MRR，纯函数。
- 跑分命令（backend 目录下）`uv run python -m teachx.evals.run_rag_eval`：
  走真实 KnowledgeService 管线（提取→切块→FTS+向量→RRF），Embedding 用 Mock。
- 基线 `backend/evals/baselines/rag_retrieval.json`（进 Git）：Hit@3=1.0、
  Recall@3=1.0、MRR=0.688；`--baseline` 对比，任一指标降超 0.05 退出码 1。
- 测试：`backend/tests/test_rag_eval.py`（7 个，含端到端底线断言）。
- 原理和面试问答见教程 22。

### E6b：回合 trace 诊断（进入 `b26b7ee`）

- `backend/src/teachx/runtime/turn_trace.py`：纯函数分析器
  `analyze_turn_events()` 读一回合持久化事件，输出状态/时长/轮数/工具行/
  发现列表；`render_trace()` 渲染文本。
- 错误码 → 责任层静态映射：模型（provider_*/rate_limited/stream_interrupted）、
  编排（turn_timeout/max_rounds_exceeded/runtime_error）、费用
  （daily_budget_exceeded）、检索（knowledge_search 失败）、工具（其他工具失败）；
  未知错误码归"未知层"不猜测。
- 警告规则：tool_retried / empty_retrieval / tool_context_truncated /
  turn_not_finalized（缺 done 事件）。
- CLI（backend 目录下）：
  `uv run python -m teachx.runtime.turn_trace --session <id> [--message <id>] [--db <path>]`。
- 测试：`backend/tests/test_turn_trace.py`（9 个，含真实回合端到端）。
- 原理和面试问答见教程 23。

## 已知限制与坑

- 新用户首次注册自动登录，第一用户是管理员。
- 旧用户 `onboarding_completed` 迁移默认已完成；新用户明确写为未完成。
- 学习目标修改文字时自动 active，完成状态不会被旧值覆盖。
- 已完成学习目标不进入提示词，但其他档案字段继续存在。
- 知识库名称目前全局唯一，不同用户不能创建同名知识库。
- 原 DeepTutor 前端仍有大量非当前主线的页面，只保证交接文档中列出的路径完成验证。
- 旧的 `/learning/practice` 页面保留兼容；新的普通用户练习入口是 `/practice`。
- 模型连接只用于聊天 Provider，不用于 Embedding。
- `TEACHX_AUTH_SECRET` 变化会使已有用户模型 Key 无法解密。
- 日预算默认关闭；真实模型测试仍应少打、短问，优先使用 Mock。
- usage 依赖供应商返回值；缺失时 TeachX 会估算并标记 `estimated`。
- 工具有有限重试和幂等执行记录；“执行成功后写终态失败”的窗口在 stale 接管时
  仍可能重复执行副作用，教程 19 有说明。
- 还没有固定评测数据集、离线回放、Recall@K/MRR、trace 和回归 dashboard。
- 还没有 MCP Client/Server、完整权限审批和沙箱执行。
- 还没有模型复杂度路由和可恢复的 durable workflow。
- Docker、PostgreSQL 和管理员用户管理不是当前阻塞项。

## 开发规则

每个大型功能必须完成：

```text
明确用户场景
→ 代码
→ 自动测试
→ 浏览器或 API 验证
→ 中文教程
→ 更新 README（影响用户时）
→ 更新 开发路线图
→ commit
→ push
```

每次任务结束前都要做文档判定。新功能必须补中文教程，小修复至少检查现有文档
是否失真。写作规则见 [规范/文档写作指南.md](规范/文档写作指南.md)。

不要：

- 在没有验证的情况下声称真实模型或线上环境完成。
- 在自动测试中读取本地真实 API Key。
- 输出或提交任何 Secret。
- 重写已经稳定的 Agent Loop。
- 删除用户本地数据库或知识库原文。
- 继续投入 Docker 或管理员功能，除非用户明确恢复。

## 文档写作与面试学习要求

用户明确要求：大型功能采用“边开发、边写技术文档”的方式，文档不仅要能运行，
还要帮助他理解并回答面试问题。每篇新功能教程至少包含：用户场景、术语解释、
可执行步骤、数据流、排障、验证证据、边界、**至少 8 个面试问答**和自测题。
教程 21（整回合超时与断线恢复）是当前标准参考。E6 完成后必须新增教程 22。
