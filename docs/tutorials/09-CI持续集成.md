# 09：CI 持续集成

## 什么是 CI

CI 是 Continuous Integration，持续集成。

它解决的问题是：

```text
代码在本地可以运行
→ 换一台机器是否还能运行？
→ 依赖是否完整？
→ 测试是否通过？
→ Docker 是否真的能构建？
```

CI 会在每次提交后，在干净的云服务器上重新执行这些步骤。

## 为什么个人项目也需要 CI

CI 不只是大公司工具。个人项目使用 CI 有三个直接收益：

1. 避免“只有你的电脑能运行”。
2. 在简历中提供可验证的工程质量证据。
3. 把容易忘记的检查自动化。

## TeachX 的 CI 工作流

文件：

```text
.github/workflows/ci.yml
```

包含三个任务：

```text
backend
→ Ruff
→ pytest

frontend
→ npm ci
→ TypeScript 类型检查
→ Next.js 生产构建

containers
→ Docker Compose 配置检查
→ 构建前后端镜像
→ 启动完整系统
→ 检查 API 和 Web
→ 输出日志
→ 清理容器
```

## 为什么分成多个 Job

如果所有内容都放在一个 Job 中：

- 某一项失败后，后面的结果不容易判断。
- 无法并行。
- 日志会混在一起。

拆成 Job 后可以并行执行：

```text
backend ─┐
         ├─→ containers
frontend ┘
```

Docker 验证依赖前两项通过，避免浪费时间构建一个明显失败的版本。

## 后端 Job 在做什么

步骤：

```text
检查代码
→ 安装 Python 3.12
→ 安装 uv
→ 根据 uv.lock 安装依赖
→ 执行 Ruff
→ 执行 pytest
```

使用 `uv.lock` 而不是随机选择最新依赖，可以保证 CI 与本地一致。

## 前端 Job 在做什么

步骤：

```text
检查代码
→ 安装 Node.js 22
→ npm ci
→ TypeScript 检查
→ Next.js 生产构建
```

使用 `npm ci`，不是 `npm install`。  
`npm ci` 严格根据 `package-lock.json` 安装，更适合 CI。

## Docker Smoke Test 是什么

Smoke Test 是“冒烟测试”，意思是先确认系统最基本的功能能启动。

它不深度测试每一个页面，而是检查：

```text
Docker Compose 能启动
API /health 返回成功
Web / 返回成功
```

核心命令：

```bash
docker compose up --build -d --wait --wait-timeout 240
curl --fail http://127.0.0.1:8010/health
curl --fail http://127.0.0.1:3000/
```

如果任何一步失败，CI 会失败。

## 为什么失败时还要输出日志

工作流使用：

```yaml
if: always()
```

即使前面的步骤失败，也会执行：

```bash
docker compose ps
docker compose logs --no-color
docker compose down -v
```

这样可以查看失败原因，同时避免 GitHub Runner 积累无用容器。

## 缓存

CI 使用缓存减少重复下载：

- uv 缓存 Python 依赖。
- npm 缓存 Node 依赖。

缓存不是正确性的来源，只是加速。锁定文件才是可重复构建的核心。

## 环境变量和 Secret

普通公开配置可以写在 YAML 中，例如：

```yaml
NEXT_PUBLIC_AUTH_ENABLED: "false"
```

真实 API Key、JWT Secret 不能写进 YAML。  
在 GitHub 中应配置 Repository Secrets，并通过：

```yaml
env:
  OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
```

传给任务。

当前 CI 不需要 API Key，因为默认使用 Mock 模型。

## 为什么 CI 不能保证程序完全正确

CI 只能证明它执行过的内容：

- 测试通过。
- 构建成功。
- 容器能启动。
- 健康接口可访问。

它不能自动证明：

- 所有用户交互都正确。
- 模型回答一定准确。
- 没有安全漏洞。
- 性能满足生产规模。

CI 是质量门槛，不是质量保证的终点。

## 常见失败原因

### Lock 文件与配置不一致

本地修改 `pyproject.toml` 或 `package.json` 后，要同步更新锁文件。

### 缺少环境变量

生产构建可能依赖 `NEXT_PUBLIC_AUTH_ENABLED` 等变量。CI 必须显式提供。

### Docker 容器启动超时

可能是依赖安装、Next.js 构建或健康检查时间过长。查看容器日志定位。

### 本地有文件，Git 没有提交

CI 从 Git 仓库重新检出代码。任何遗漏文件都会在 CI 暴露。

## 小练习

1. 在本地执行一次 `docker compose config`。
2. 增加一个只在 Pull Request 执行的 lint 任务。
3. 为 CI 添加测试覆盖率报告。
4. 添加缓存命中率检查。
5. 配置 `OPENAI_API_KEY` Secret 后执行真实模型 Smoke Test。
