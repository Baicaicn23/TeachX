# 01：一次提问的完整旅程

## 先用人话理解

可以把 TeachX 想成一家餐厅：

- 浏览器是顾客点菜的地方。
- FastAPI 是前台。
- AgentRuntime 是服务员。
- 模型是厨师。
- 工具是厨房里的烤箱、计算器等设备。
- SQLite 是订单档案柜。

顾客不会直接冲进厨房。请求会途经多个环节，每个环节只负责自己的事情。

## 从输入框开始

用户在聊天框输入：

```text
计算 12 * 8
```

前端不会直接调用 Python 函数。它先把请求组织成协议消息，通过 WebSocket 发出。

协议消息的重要字段包括：

```json
{
  "type": "start_turn",
  "protocol_version": "2.0",
  "content": "计算 12 * 8",
  "capability": "chat"
}
```

`type` 告诉后端“这是开始一个回合”。
`content` 是用户真正输入的内容。
`capability` 决定使用哪种教学模式。

## WebSocket 入口

后端收到消息的位置在：

```text
backend/src/teachx/api/routes/ws.py
```

核心逻辑可以简化成：

```python
command = StartTurnCommand.model_validate(payload)

async for event in container.runtime.run_turn(command):
    await send(websocket, event)
```

这里有两个重要概念：

- `model_validate()` 检查前端传来的数据结构是否合法。
- `async for` 逐个读取 AgentRuntime 产生的流式事件。

## AgentRuntime 做了什么

`AgentRuntime` 位于：

```text
backend/src/teachx/runtime/engine.py
```

它按顺序执行：

1. 确保会话存在。
2. 保存用户消息。
3. 组装消息上下文。
4. 调用模型。
5. 如果模型要调用工具，执行工具并再次调用模型。
6. 把最终回答保存到数据库。
7. 发送 `done` 事件。

## 消息上下文是什么

模型不能直接读取数据库，也不会自动记得所有内容。后端必须把历史整理成消息列表：

```python
[
    {"role": "system", "content": "你是 TeachX..."},
    {"role": "user", "content": "第一个问题"},
    {"role": "assistant", "content": "第一个回答"},
    {"role": "user", "content": "计算 12 * 8"},
]
```

三种基本角色的作用：

- `system`：告诉模型身份、规则和回答方式。
- `user`：用户说过的话。
- `assistant`：模型之前给出的回答。

工具调用时还会出现 `tool` 角色，下一章会详细解释。

## 为什么需要 Repository

如果 AgentRuntime 直接写 SQL，会导致业务逻辑和数据库细节混在一起。
因此项目增加了 `SessionRepository`：

```text
AgentRuntime 只调用：
repository.add_message(...)

Repository 内部才关心：
INSERT INTO messages ...
```

这样做的好处是：以后从 SQLite 换成 PostgreSQL 时，AgentRuntime 不需要重写。

## WebSocket 事件是什么

后端并不只返回一段最终字符串，而是发送多个事件：

```text
session
stage_start
content
content
content
stage_end
result
done
```

前端收到 `content` 后追加文字，所以用户能看到内容逐渐出现。

## 为什么保存的是消息而不是一段文本

只保存一整段文本会丢失很多信息：

- 哪一部分是用户说的？
- 哪一部分是助手的回答？
- 这条回答用了哪个能力模式？
- 是否发生了工具调用？

因此 TeachX 把每条消息保存为独立记录，并把事件也保存在助手消息中。

## 常见误区

### “前端直接调用模型最省事”

短期可行，但会暴露 API Key，也无法可靠执行后端工具，更不能统一保存状态。

### “模型自己会记住历史”

模型是无状态的。每一次调用都需要后端把必要的历史重新传进去。

### “WebSocket 只是更快的 HTTP”

WebSocket 的价值是双向且持续的连接。它适合多个连续事件，而不是只返回一个响应。
