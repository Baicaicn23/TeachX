# 25：意图识别与多 Agent 路由——TeachX 怎么判断"你想干什么"

> 本章适合第一次接触"意图识别"（Intent Classification）和"多 Agent 路由"
> （Multi-Agent Routing）的读者。读完后，你将能够：说清楚 TeachX 在用户发出
> 消息之后、模型开始回答之前做了什么；解释六个意图类别和六个子 agent 分别是
> 什么；跑通意图评测并看懂分数；回答面试官关于"为什么不用框架""识别错了
> 怎么办""工具最小权限怎么落地"的追问。

## 为什么需要它

先看没有意图路由时的状况。在引入这一层之前，TeachX 的每个回合都是同一条
流水线：同一个系统提示词、同一份工具清单（计算器，选中知识库时加检索）。
用户的"帮我算一下 12 * 8"和"给我出 5 道练习题"得到的是同一种回答风格的
模型、同一组可用工具。

这有两个实际问题：

1. **提示词没有角色感。** 出题、讲概念、报进度是三种不同的"工作模式"，
   混用一个提示词，模型只能在一句话里兼顾所有风格，哪种都不够专业。
2. **工具权限没有边界。** 出题时模型也能发起知识检索——它可能检索到一段
   不相关的资料然后被带偏；查询进度时理论上也能触碰任何工具。权限应该是
   "这个任务需要什么就给什么"，而不是"全部都开着"。

意图识别 + 多 Agent 路由就是在回合开始前补上这一层判断：先弄清楚用户想
干什么（意图），再把任务交给一个配置专属的"子 agent"（专属提示词 + 专属
工具策略）。这也是业内大佬对项目"把一个真实 Agent 做深"建议的第一步
（见开发路线图的「下一阶段：端到端 Agent 深度」）。

## 最终结果

完成本章操作后，你应该能在浏览器和 WebSocket 里看到：

```text
浏览器发送：帮我算一下 12 * 8 等于多少
回合状态条：已完成 · 0s · 1 次工具调用
回答内容：计算结果已经得到：96。
持久化 metadata：{"intent": "calculation", "agent": "calculator",
                  "intent_detector": "rule", "intent_confidence": 0.95}

浏览器发送：给我出 5 道线性代数练习题
回合状态条：已完成 · 1s          ← 没有"工具调用"字样
持久化 metadata：{"intent": "practice", "agent": "practice"}
```

计算意图被路由给 calculator 子 agent（配了计算器工具），练习意图被路由给
practice 子 agent（一个工具都没有，出题全靠模型本身）。

## 前置条件

- 已能运行 `./scripts/dev.sh` 和 `./scripts/check.sh`（教程 00）。
- 不需要任何 API Key：本章的自动测试和评测全部走 Mock 模型与规则分类器。
- 需要理解的三个词（现在解释，后文直接用）：
  - **意图（intent）**：用户这条消息想达成的目标类型，例如"出题"或"计算"。
  - **子 agent（sub-agent）**：不是另一个程序，而是一份配置——专属系统提示词
    + 允许使用的工具集合。同一个模型，戴上不同的"工牌"上岗。
  - **路由（routing）**：从意图到子 agent 配置的查表过程。

## 它是怎么工作的

一次回合的完整数据流，新增部分在第一步：

```text
用户消息
→ ① 意图识别(runtime/intents.py)
     规则分类器先判一次(纯函数,零成本)
     ├─ 规则给出强信号(置信度 ≥ 0.9,如数学表达式)→ 直接采用
     ├─ 否则调 LLM 输出 {"intent": "...", "confidence": ...}(低 token)
     │   ├─ provider 是 Mock → 跳过 LLM,直接用规则(测试确定性)
     │   └─ JSON 解析失败 / 调用异常 → 回退规则结果
     └─ 查路由表 AGENT_PROFILES 得到子 agent 配置
→ ② 装配工具集合(_enabled_tools_for)
     基础集 = 用户显式选择,或子 agent 默认集(前端默认发空列表,视同未选择)
     + MCP 动具(仅 allow_mcp_tools 的子 agent) + 知识库联动(检索类)
     − 子 agent 拒绝集(practice 拒绝 knowledge_search;progress 全部拒绝)
→ ③ 组装系统提示词
     能力提示词(chat/解题/出题) + 子 agent 专属提示词 + 学习档案
→ ④ 原有 Agent Loop 跑完回合(E1~E5 的重试/幂等/超时全部不变)
→ ⑤ 事件持久化:tool_call / result / done / 消息 metadata 都带
     intent、intent_confidence、intent_detector、agent 字段
```

### 六个意图和六个子 agent

| 意图 | 子 agent | 默认工具 | 拒绝工具 | 专属提示词的作用 |
| --- | --- | --- | --- | --- |
| `concept_explain` | tutor | calculator | — | 讲解导师：拆概念、给例子、有知识库先检索 |
| `practice` | practice | （无） | knowledge_search | 出题教练：出有梯度的题，先不公布答案 |
| `progress` | progress | （无） | 全部（deny_all） | 进度报告员：只依据档案与对话，不编数字 |
| `retrieval` | retriever | knowledge_search | — | 检索助手：改写检索词、给来源、找不到如实说 |
| `calculation` | calculator | calculator | knowledge_search | 计算助手：必须用工具，不许心算 |
| `smalltalk` / 未识别 | chat | calculator | — | 默认对话，与引入路由之前完全一致 |

### 规则分类器为什么这样排序

`classify_by_rules` 的判定顺序是"信号越具体越优先"：

1. 数学表达式正则（`7 * 9`、`3^4`，并排除 `2026-10` 这种日期形态）；
2. 进度词（"学习进度"、"掌握度"、"离目标"）；
3. 练习词（"出题"、"考考我"、`出 5 道` 正则）；
4. 检索词（"我的资料"、"知识库"、"根据文档"）——放在概念词之前，因为
   "在我的资料里找一下特征值的**定义**"同时命中两类，用户明确提到资料来源
   时应该按检索处理；
5. 概念词（"什么是"、"为什么"、"解释一下"）；
6. 闲聊词 / 兜底（未命中任何词 → smalltalk，置信度 0.3）。

兜底归入 smalltalk 而不是新增"unknown"类别，是为了让意图枚举封闭：路由表
只有六行，任何输入都能落到一行上，未识别自然走默认对话。

### LLM 识别的输入输出约定

规则置信度低于 0.9 时，运行时用 `provider.complete()` 发一次低 token 调用
（`max_output_tokens=64`），系统提示词给出六类定义，要求只输出一行 JSON：

```json
{"intent": "practice", "confidence": 0.9}
```

`parse_intent_json` 做三层防御：剥掉模型顺手包裹的 markdown 代码块；校验
intent 必须在枚举内（防止模型发明第四个类别）；confidence 截断到 0~1。
任何一步失败都返回 None，detect_intent 回退规则结果——**意图识别永远不能
把用户的回合搞失败**，这是这一层的底线。

### 成本意识：什么时候不调 LLM

三种情况会跳过意图 LLM 调用，这是刻意的成本设计：

- 规则给出强信号（≥0.9）——数学表达式这种确定性判定，问了也是白问；
- provider 是 Mock——它的输出不遵循 JSON 约定，问了没有信息量，这也保证
  自动测试全程确定性、零 API 消耗；
- 今日预算已超限且策略是 block——本轮注定被阻止，不为识别白花 token。

意图调用的 token 会以 `call_kind="intent_detection"` 记入 usage（教程 18
的费用链路），前端能看到这一笔消耗。

### 工具最小权限为什么做两层

第一层是 schema 级：`_enabled_tools_for` 计算出的工具清单决定"给模型看
什么"。模型通常只会调用清单里的工具。但这只是软约束——提示词注入或幻觉
仍可能让模型请求清单外的工具。第二层是执行级：`_execute_tool_batch` 在
真正执行前再查一次子 agent 的拒绝策略，被拒的调用不执行、返回
`error_code="tool_not_allowed"` 的失败结果，模型拿到失败后自行调整。
两层的判定都来自同一份 AgentProfile，不会出现"schema 说不行、执行说行"的
分裂。

两层只有"拒绝集"（黑名单）是硬的；默认对话的黑名单是空的，保持引入路由
之前的行为——用户显式选择的工具不被路由推翻。路由收窄权限，不扩大权限。

## 常见错误

| 现象 | 原因 | 处理方式 |
| --- | --- | --- |
| 浏览器发计算消息但没有工具调用 | 后端进程还是旧代码（改完代码没重启） | 重启 `./scripts/dev.sh`；`--reload` 只对 backend 生效 |
| `done` 事件里没有 intent 字段 | 配置了 `TEACHX_INTENT_ENABLED=false`，或回合在预算阻止前早退 | 检查环境变量；预算阻止的 done 也会带 intent，确认识别层没被整体关闭 |
| 意图判错（如"帮我看看第 3-4 章的内容"被判为 calculation） | 规则分类器把 `3-4` 当成了减法表达式 | 这是已知边界（见下）；对真实流量可在 LLM 识别开启时由模型纠偏，或向词表/正则贡献修复 + 补评测样本 |
| 改了词表后 `check.sh` 失败 | 意图评测基线回归（准确率下降超容差） | 跑 `uv run python -m teachx.evals.run_intent_eval` 看误分类明细；是改进就把 `--save` 的新基线一起提交，是退化就修回去 |
| 测试报 `complete_calls == 1` 之类失败 | 自定义测试 Provider 的 complete 被意图识别多调了一次 | 在该测试的 AgentRuntime 构造里加 `intent_llm_enabled=False`（参考 test_cost_control 的做法） |

## 当前边界

诚实说明这套实现还没有做的事：

- **意图只有六类。** "帮我总结这篇文档""翻译这段话"等会落入兜底
  smalltalk，走默认对话。扩类只需在枚举、词表、路由表、评测集四处各加一行，
  这是有意保留的低门槛扩展点。
- **规则分类器有误判边界。** 中文算式（"1024 除以 8"）已覆盖，但"第 3-4 章"
  仍会被正则当成减法；LLM 识别开启时真实流量由模型纠偏，纯规则模式（关闭
  LLM）会保留这类错误。
- **进度子 agent 还没有读数据库的工具。** 它只依据注入提示词的学习档案
  （目标、进度百分比）和当前对话回答；练习掌握度等数据还没暴露成只读工具。
- **前端没有展示意图。** intent 只出现在事件和持久化 metadata 里，界面不
  显示"已识别意图：练习"——这是后续的小任务。
- **意图评测集是规则考卷。** 38 条样本全部可以离线确定性复现；LLM 识别的
  准确率没有进 CI（需要真实额度），目前由测试桩验证解析与回退逻辑。
- **练习子 agent 与 /practice 页面没有打通。** 出题 agent 生成题目文本，
  但不会写入练习队列（那是 PracticeService 的领地，教程 15）。

## 面试问答

**Q1：为什么要在 Agent Loop 前面单独加一层意图识别，而不是把这个判断交给
模型自己在提示词里做？**

模型当然可以"自己看着办"，但那样三个问题没有答案：判断结果不可观测（你
不知道它把自己当成了什么角色）、工具权限不可控（提示词说"别用检索"挡不住
注入）、行为不可测试（无法写确定性断言）。把判断提出来变成显式的
intent 字段后，路由可查表复现、权限可按意图收窄、评测集可以像考卷一样跑分。
这也是多 Agent 系统的通用经验：**编排决策要做成数据，不要做成模型的内心
活动。**

**Q2：意图识别为什么用"规则 + LLM"两层，而不是纯 LLM 或纯规则？**

纯 LLM：每回合多一次调用的延迟和费用，而且简单意图（`7*9`）根本不需要问
模型；服务不可用时整个产品不可用。纯规则：中文表达太灵活，词表永远追不完，
"随便来点题目呗"这种说法规则就接不住。所以取分层：规则给确定性和兜底，
LLM 给泛化能力，LLM 失败时系统退化成纯规则而不是退化成不可用。强信号规则
命中时跳过 LLM，是把钱花在刀刃上的折中。

**Q3：LLM 意图识别输出的是自由文本，你怎么保证解析不炸？**

三道防线 + 一条底线。防线一：提示词里给了严格的输出约定（一行 JSON、不要
解释）。防线二：`parse_intent_json` 容错解析——剥 markdown 围栏、截取首个
`{` 到最后一个 `}`、校验 intent 必须在枚举内、confidence 截断。防线三：
`detect_intent` 整体 try/except，任何异常（包括 provider 超时）都回退规则
结果。底线是：意图识别是回合的"前置判断"，它自己永远不能成为回合失败的
原因——最坏结果就是这次路由退回默认对话。

**Q4：为什么练习子 agent 连检索工具都不给？这不是能力损失吗？**

出题依赖的是模型的知识和对话上下文，检索进来的片段反而会把题目"锚定"到
某段资料上，破坏梯度设计；而且练习场景没有任何需要查证的事实。这就是最小
权限的实际含义：不是"有备无患地全给"，而是"这个任务用不到的就是不该有"。
工程收益是实打实的：工具清单更短（schema 更少 token）、模型行为更聚焦、
并且从根上杜绝了"练习时检索到不相关资料被带偏"这类故障。

**Q5：只把工具从 schema 里拿掉不就行了吗，为什么执行层还要再拦一次？**

Schema 是软约束：它只影响模型"通常"调用什么。一个被提示词注入或幻觉的
模型完全可能请求清单外的工具，而旧运行时的逻辑是"模型请求什么就执行什么"。
所以执行层必须用同一份 AgentProfile 再判一次：被拒的调用不执行，返回
`tool_not_allowed` 失败结果，模型收到失败后自行组织回答。这和 E3 的参数
脱敏是同一个哲学：**安全边界要放在执行路径上，不能只放在"请求它别这么干"
上。** 自动测试里有一条专门模拟这个场景。

**Q6：意图判错了怎么办？用户问"帮我看看第 3-4 章"被当成计算，会发生什么？**

先说损害边界：判错的代价是"子 agent 配置不合适"，不是"回合失败"。计算
agent 配了计算器，模型面对"看看第 3-4 章"不会硬调工具，还是会正常回答——
最坏情况是提示词角色不贴切。缓解手段按优先级：LLM 识别开启时模型会纠偏
规则的误判；评测集把已知误判样本收进去，修词表时基线门禁防止改好一处改坏
三处；产品上用户换一种说法天然自愈。这也解释了为什么意图枚举要封闭 + 兜底
进默认对话：兜底路径永远是安全的。

**Q7：这套路由和 LangChain / LlamaIndex 之类的框架比，缺什么、多什么？**

缺的是生态：现成的 RouterChain、Agent 类型、工具市场。多的是可控性和可讲
性：整条链路两百行左右（intents.py 一个文件 + engine 的两处接缝），每一步
——规则顺序、JSON 容错、拒绝集、事件字段——都是自己写的、可测试的、能在
面试里展开到实现细节的。这个项目的定位就是展示 Agent Harness 的工程能力：
框架会掩盖"意图识别失败怎么回退""权限怎么在执行层拦截"这些真正值钱的
判断。学习版标准下，手写是特性不是缺陷。

**Q8：意图识别这一步会增加多少延迟和费用？怎么量化的？**

规则路径是纯函数，微秒级、零费用。LLM 路径多一次 `complete()` 调用，
`max_output_tokens=64`（输出侧费用有硬上界），输入是六类定义 + 截断到
500 字符的用户消息。三种情况会跳过：强规则信号、Mock Provider、预算已超限。
每一次意图调用的 token 以 `call_kind="intent_detection"` 进 usage 表，前端
的本轮/累计统计包含它——费用不是估出来的，是记出来的。

**Q9：评测集只有 38 条，准确率 100% 有说服力吗？**

要诚实：38 条、规则自检、全对，说明的是"规则覆盖了这 38 种表达"，不等于
真实流量准确率 90%+。它的价值在于**回归门禁**：以后任何人改词表、改正则、
扩意图，38 条考卷 + 0.05 容差能立刻暴露"改好一处改坏三处"。提高说服力的
路径也已经铺好：往数据集里持续添加真实误判样本（门禁会强制你修到达标），
以及用真实流量日志做人工标注对比。小考卷能抓回归，不代表分布——这个限制
在检索评测（教程 22）里也一样，是这类离线评测的通病。

**Q10：如果要把这个设计推到生产，下一批要改什么？**

按优先级：一是意图识别的在线观测——intent 维度统计路由分布和纠偏率
（P3 的监控聚合会覆盖）；二是把"进度"做成真正的只读工具（查掌握度、查复习
队列），让 progress agent 有数据可依；三是意图的上下文连续性——用户连续
追问时不应每条消息重新分类，需要"继承上一回合意图 + 显式切换信号"的规则；
四是评测集从手写样本迁移到真实流量抽样标注。每一条都能单独讲十分钟的取舍，
这里不展开。
