# 13：首次使用引导

## 这一章解决什么问题

新用户注册后，如果直接进入聊天页，会遇到几个问题：

- 不知道应该先上传资料，还是直接提问。
- 不知道 TeachX 的回答会按什么年级和风格生成。
- 个人主页里有很多设置，但不清楚哪些最重要。
- 旧用户已经配置过账号，不应该再被强制引导一次。

U3 的目标是让新用户在约一分钟内完成最基础的个性化设置：

```text
学习阶段
→ 学习目标
→ 讲解偏好
→ 可选上传第一份资料
→ 进入聊天
```

整个流程可以跳过。跳过不是失败，而是明确记录“以后不用再自动显示引导”。

## 为什么不能只判断学习档案是否为空

最简单的实现是：

```text
学习档案为空 → 显示引导
学习档案不为空 → 不显示引导
```

这个办法看起来省事，但会误伤旧用户。旧用户可能已经注册很久，只是没有填写
年龄、年级等档案字段。如果直接用“档案为空”判断，他们登录后会被强迫重新引导。

所以 U3 使用一个独立字段：

```text
users.onboarding_completed
```

含义是“这个账号是否已经做过首次引导，或者明确跳过”。

数据库迁移规则也很重要：

```text
旧数据库新增 onboarding_completed 列
→ 已有用户默认值为 1
→ 旧用户视为已经完成

新用户注册
→ 明确写入 0
→ 登录后进入首次引导
```

这样“是否完成引导”和“是否填写过档案”不会混在一起。

对应代码：

- `backend/src/teachx/storage/database.py`
- `backend/src/teachx/auth/models.py`
- `backend/src/teachx/auth/service.py`

## 注册后为什么能直接进入引导

旧流程是：

```text
注册
→ 跳转登录页
→ 用户再次输入用户名和密码
→ 进入聊天
```

这会增加一次不必要的操作。U3 改为注册成功后立即签发登录 Cookie：

```text
注册成功
→ 后端写入 HttpOnly Cookie
→ 前端跳转 /onboarding
```

后端仍然使用原来的 JWT 和 Cookie 逻辑，没有创建第二套认证机制。

## 后端接口

U3 增加两个接口：

```text
GET  /api/auth/onboarding
POST /api/auth/onboarding/complete
```

读取状态：

```json
{
  "available": true,
  "completed": false,
  "learner_profile": {}
}
```

完成或跳过：

```json
{
  "completed": true
}
```

学习阶段、目标和讲解偏好仍然写入原有学习档案接口：

```text
PUT /api/auth/profile/learner-profile
```

这样做的好处是：

- 引导页不保存另一份重复的学习档案。
- 个人主页修改后，聊天页读取的是同一份数据。
- Agent Runtime 原有每回合读取档案的逻辑不需要重写。

`learning_goal` 也加入了个性化提示词：

```text
学习档案
→ AgentRuntime 每回合读取
→ 注入系统提示词
→ 模型围绕用户目标组织回答
```

## 前端页面结构

主页面：

```text
frontend/app/(auth)/onboarding/page.tsx
```

页面分为三步：

1. 选择学习阶段。
2. 填写学习目标。
3. 选择讲解偏好，并可选上传资料。

状态管理由页面自身完成，不引入新的全局 Store。原因是引导只在短时间内使用，
生命周期结束后不需要其他页面订阅。

接口封装：

```text
frontend/lib/onboarding-api.ts
```

它负责：

- 读取引导状态。
- 标记引导完成。
- 创建用户自己的资料知识库。
- 重试时复用已经创建的知识库，避免重复名称。

## 工作区门禁

只修改注册页还不够。一个新用户仍然可以手动打开：

```text
/chat
/profile
```

因此工作区和工具页增加了：

```text
frontend/components/auth/OnboardingGate.tsx
```

门禁逻辑：

```text
认证关闭
→ 不拦截

未登录
→ 交给原有认证流程

已登录且 onboarding_completed = true
→ 正常显示页面

已登录且 onboarding_completed = false
→ 跳转 /onboarding
```

如果状态接口暂时失败，门禁不会让整个聊天不可用。它只在后端明确返回“尚未完成”
时跳转。这延续了聊天页个性化状态“失败不能阻塞核心功能”的设计原则。

## 跳过和完成有什么区别

从数据上看，两者最终都写入：

```text
onboarding_completed = 1
```

区别只在于是否保存本次填写内容：

```text
“暂时跳过”
→ 不写学习档案
→ 标记完成
→ 进入聊天

“完成设置”
→ 保存学习档案
→ 可选上传资料
→ 标记完成
→ 进入聊天
```

所以刷新、重新登录或第二天再打开时，都不会重新自动进入引导。用户仍可在
`/profile` 中随时修改学习档案。

## 可选资料上传

前端复用现有知识库接口：

```text
POST /api/knowledge-bases
POST /api/knowledge-bases/{name}/upload
```

知识库名称使用用户 ID 生成，例如：

```text
学习资料-c358678981544900
```

这样可以避免两个用户都创建“我的资料”时发生全局名称冲突。

如果创建过程中上传失败，用户重试时会先检查知识库是否存在：

```text
不存在
→ 创建知识库并上传

已存在
→ 直接补充上传
```

资料上传属于增强体验，不是完成引导的前置条件。

## 常见误解

### 1. 引导完成是否等于资料必须上传？

不是。资料是可选项。用户可以不选任何资料直接完成，也可以直接跳过。

### 2. 跳过是否删除学习档案？

不会。跳过只是不写本次表单内容，也不会删除用户以前保存的档案。

### 3. 认证关闭时本地用户会不会被引导？

不会。认证关闭时没有多用户注册流程，本地用户默认视为已经完成。

### 4. 以后怎样增加新的引导步骤？

优先扩展 `/onboarding` 和现有接口，不要重新发明一套“首次设置档案”。如果需要
记录更细的步骤完成情况，再为 `users` 增加独立字段，而不是通过猜测其他字段是否为空。
