# 21：整回合超时、最大轮数与断线恢复提示

> 本章适合已经读完[教程 19](19-工具执行政策与重试.md)和
> [教程 20](20-多工具执行策略.md)的读者。读完后,你应该能够解释:
> 单工具超时和整回合超时为什么是两层不同的保护,最大轮数耗尽时怎样诚实失败,
> 以及前端如何让用户看懂失败原因并一键重试。

## 这一章解决什么问题

E1 给了**单个工具**超时保护,但一个回合是"多轮模型调用 × 多个工具"的组合,
任何一处都可能拖住整个回合:

```text
场景 1:模型流式输出突然停住,一个字都不再发(半途挂起)
场景 2:模型陷入调用工具的循环,永远不给最终回答
场景 3:回答已经生成了一半,此时出问题——丢掉它还是保存它?
```

更糟的是旧版的行为:最大轮数耗尽时,系统会发一段罐头文本
("本轮推理达到最大工具调用轮数,请缩小问题范围后重试")当作**正常回答**保存,
前端显示"完成"。用户看到一段看似回答的道歉文,不知道出了什么问题、不能重试——
这就是"部分回答伪装成完整回答"。

E5 的三条修复:

```text
1. 整回合时间预算(TEACHX_TURN_TIMEOUT_SECONDS,默认 300 秒,0 关闭)
2. max_rounds 耗尽 → 诚实失败:error 事件 + done.status=failed
3. 已生成的部分回答不丢弃:保存并标记 partial=true,前端显示可重试
```

## 一、两层超时的分工

| 层 | 管什么 | 谁负责 |
| --- | --- | --- |
| 单工具超时(E1) | 一次工具执行最多等多久 | ToolRegistry 的 ToolPolicy |
| 整回合超时(E5) | 一次用户提问的总时间预算 | AgentRuntime 的 deadline |

为什么单工具超时不够?回合里有 N 轮模型调用、每轮最多 M 个工具,就算每个都
在各自超时内完成,总时间仍可能远超用户耐心。整回合预算是**总闸**,单工具是
**分闸**;分闸漏掉的(比如模型流挂起、循环调用工具)由总闸兜住。

实现上,回合开始时算一个截止时间(deadline),三个地方检查:

```text
每轮开始时          → 预算已耗尽就不再发起模型调用
流式每个片段之间     → 下一片等待时间超过剩余预算就判定超时
每批工具执行前       → 用剩余预算包一层 wait_for
```

第三个检查点用的是 `asyncio.wait_for`,超时会**取消**正在执行的工具批次——
这是刻意的:预算耗尽后继续执行只会浪费资源,而且有副作用的工具在用户已经
放弃后还去执行,体验更糟。

## 二、流挂起怎么发现:每个片段一个看门狗

"模型流停住不发字"是最隐蔽的故障。如果只在轮与轮之间检查预算,一个挂起的流
永远不会推进到下一个检查点。

解决方法是把流的每次取下一个片段(`__anext__`)也放进 `wait_for`:

```python
item = await asyncio.wait_for(
    _next_chunk(stream_iterator),
    timeout=剩余预算,
)
```

一个实现细节值得面试展开:`StopAsyncIteration` 不能穿过 `wait_for` 包装的
Task(Python 会把它当成协程错误),所以先在 `_next_chunk` 里把它转成一个
哨兵值 `_STREAM_END`。这是异步原语边界的典型坑。

## 三、max_rounds 耗尽:从罐头文本到诚实失败

旧行为与新行为的对比:

| | 旧行为 | 新行为(E5) |
| --- | --- | --- |
| 无内容时 | 罐头文本存成"回答",done=completed | error 事件 + done=failed,不保存假回答 |
| 有部分内容时 | 完整保存,done=completed(伪装) | 保存 + `partial=true`,done=failed |
| 用户看到 | 一段道歉文,像正常回答 | 错误原因 + "可重试"按钮 + 已生成的部分 |

判断"耗尽"用的是 Python 的 `for...else`:循环没有被 `break`(即模型始终没有
给出最终回答)而自然结束时,`else` 分支执行,标记 `hit_max_rounds`。

`error` 事件契约:

```json
{
  "error_code": "max_rounds_exceeded",
  "retryable": true,
  "turn_terminal": true,
  "status": "failed"
}
```

## 四、部分回答的保存契约

超时或轮数耗尽时,`final_content_parts` 里可能已经有真实内容(用户看着它
一个字一个字流出来的)。丢掉它是错的——用户会以为幻觉。

新契约:**有内容就保存,但打上标记**。

```json
result 事件: { "content": "已生成的部分", "partial": true }
助手消息 metadata: { "partial": true, "turn_error_code": "turn_timeout" }
done 事件: { "status": "failed", "partial": true, "retryable": true }
```

关键点:`done.status` 是 `failed` 而不是新增一个 `partial` 状态。原因有二:
一是前端的状态机已经把 `failed` 处理得很完整(重试按钮、错误展示);
二是"这回合失败了"是事实,"保留了部分内容"是补充信息——用 `partial` 字段
表达补充信息,比用新状态值表达事实更诚实,也让旧客户端不至于遇到未知状态。

## 五、统一错误码

E5 把三个"回合没有正常结束"的错误统一成稳定代码:

| error_code | 含义 | retryable | 来源 |
| --- | --- | --- | --- |
| `turn_timeout` | 整回合时间预算耗尽 | true | AgentRuntime(E5 新增) |
| `max_rounds_exceeded` | 工具调用轮数耗尽 | true | AgentRuntime(E5 新增) |
| `stream_interrupted` | 模型流式中断 | true | Provider(由 `provider_stream_error` 更名统一) |

`retryable: true` 是给前端的信号:这不是用户输入错了,重新发送大概率能成功。

## 六、前端如何展示(已有机制,无需新组件)

前端在 DeepTutor 继承的状态机里**早就有**这套机制,E5 做的是让后端发出
前端一直在等的事件:

```text
error 事件(turn_terminal + retryable)
→ 消息列表找到最后一个终端错误,展示其 content(失败原因)
→ retryable=true 时显示"重新生成"按钮
→ 部分内容正常渲染在错误提示上方
done.status=failed
→ 会话标记 lastTurnFailed → 重发按钮可用
```

验收口径:超时后用户能看到原因("本轮回答超时,已生成的部分回答已保留,可以重试"),
能点重试,部分回答带着 partial 标记存在,不会伪装成完整回答。

## 八、真实验证

引擎输出即 WebSocket 发给前端的线上格式(ws.py 只加序号)。超时回合的
完整事件序列:

```text
事件类型: session → stage_start → content → result → error → done
done: status=failed, error_code=turn_timeout, retryable=true, partial=true
result.content: 已经生成的部分回答。
error 文案: 本轮回答超时,已停止后续模型调用。已生成的部分回答已保留,可以重试。

```

## 九、当前边界

- 超时判定发生在事件边界(片段之间、批次前后),不是抢占式中断——一个单次
  慢的工具调用要等到自己的超时或回合剩余预算触发,粒度是秒级。
- `stream_interrupted` 只统一了 OpenAI 兼容 Provider 的未知异常映射;
  Mock Provider 不产生该错误。
- 断线恢复只覆盖"回合失败后重试";用户关闭浏览器再回来时,进行中的回合
  不会恢复执行(没有 durable workflow,那是 E10 的范围)。
- 预算耗尽(budget_exceeded)仍是"完成 + 通知"语义,因为它是受控停止,
  内容是完整的,不属于伪装。

## 十、面试问答

### 1. 为什么单工具超时之外还需要整回合超时?

单工具超时只约束一次工具执行;回合是 N 轮模型调用 × M 个工具的组合,每个
都合规,总量仍可能无限大(比如模型循环调用工具)。整回合预算是总闸,保护的是
用户的总等待时间和服务器资源,与分闸(单工具超时)是两层独立的防御。

### 2. deadline 检查点为什么选在这三个位置?

轮开始、流片段之间、工具批次之前——它们是回合的自然暂停点,检查成本几乎为零。
反过来,如果每个字符或每个事件循环都查一次,开销和代码噪音都会增加,而精度
只提升毫秒级。在暂停点检查是"成本与响应性"的平衡。

### 3. `wait_for` 超时会取消工具批次,这安全吗?

对 TeachX 当前的只读工具(calculator、knowledge_search),取消只是丢弃进行中的
协程,没有副作用。对有副作用的工具,取消发生在"用户已放弃"的语境下:继续执行
比取消更糟。E2 的幂等记录会如实记录这次取消(可能停在 running,由 stale 接管
兜底),不会造成重复副作用。

### 4. 为什么 done.status 用 failed 而不是新增 partial 状态?

status 表达事实("这回合失败了"),partial 表达补充信息("保留了部分内容")。
引入新状态值要求所有消费方(前端状态机、历史加载、测试)都认识它,成本高;
而 failed + partial 字段让旧代码也能正确处理失败,新代码多读一个字段获得
更细的信息。这是向后兼容的契约演进。

### 5. 部分回答为什么值得保存?

它已经流到用户屏幕上了——用户"看过"这段内容。如果刷新后消失,用户会怀疑
自己的记忆;如果数据库里没有,后续引用也无从谈起。保存 + 标记的方案让
"看到过的"和"完整的"分开:内容在,但 `partial=true` 明确告诉所有人它不完整。

### 6. `StopAsyncIteration` 不能穿过 wait_for 是怎么回事?

`asyncio.wait_for` 把协程包成 Task;Task 里抛 `StopAsyncIteration` 属于
"协程以迭代结束信号终止",Python 会把它转成 RuntimeError,而不是原样传播。
所以先包一层 `_next_chunk`,把 `StopAsyncIteration` 转成普通哨兵值返回。
这是异步原语边界的经典坑:异常语义在生成器和 Task 之间不透明。

### 7. retryable=true 的判断依据是什么?

三类错误(超时、轮数耗尽、流中断)的共同点:它们是环境性的,不是用户输入
错误。重试大概率遇到正常的网络和模型,所以标记可重试。反过来,参数校验失败、
权限拒绝永远不该标 retryable——重试一万次结果相同。

### 8. 前端为什么不需要新组件?

DeepTutor 继承的前端早就实现了"终端错误展示 + retryable 驱动重试按钮 +
失败会话可重发"的机制,问题只在后端从未发出过正确的信号(一直用 completed
+ 罐头文本伪装)。E5 修的是契约而不是 UI——这提示我们:改跨端行为时,先审计
两端已有的机制,常常比新写组件更有效。

### 9. 超时后标题还会生成吗?

会——标题生成本身有 Provider 超时约束,且只在首回合发生,耗时可控。即使
回合因超时失败,首回合的会话标题仍然有价值(用户重试时看到的是有名字的会话)。
如果标题生成也超时,本地截断标题兜底(见教程 18)。

### 10. 这个设计和"断线恢复"是什么关系?

E5 覆盖的是"回合失败 → 用户看到原因 → 一键重试"的**用户路径**恢复。
真正的断线恢复(服务器崩溃后,进行中的回合从断点继续)需要把回合状态
持久化成可恢复的工作流,那是 E10 durable workflow 的范围。面试时把两者
区分开,能体现对"恢复"这个词不同层次的理解。
