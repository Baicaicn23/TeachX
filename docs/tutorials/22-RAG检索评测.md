# 22:评测——怎么证明你的检索是好的

> 本章适合第一次接触"评测(Evaluation)"的读者。读完后,你应该能回答面试里
> 几乎必问的问题:**"你怎么知道你的 RAG/Agent 是好的?改了代码之后怎么知道
> 没有变差?"**

## 这一章解决什么问题

到目前为止,TeachX 的检索质量只能靠"试几句话感觉一下"。这有两个大问题:

1. **说不清**。面试官问"你的检索效果怎么样",只能回答"我觉得还行"。
2. **守不住**。改了切块大小、换了排序公式,检索可能悄悄退化,没有人知道。

E6 第一部分交付的是一套**学习版评测**,三个文件加一条命令:

```text
backend/evals/datasets/rag_retrieval.json   固定评测集(语料 + 查询 + 标准答案)
backend/src/teachx/evals/metrics.py          三个指标(Hit@K / Recall@K / MRR)
backend/src/teachx/evals/run_rag_eval.py     跑分命令 + 基线回归对比
```

## 一、评测集(golden dataset)是什么

一份**固定的考卷**:语料、考题、标准答案都写死在 JSON 里,永远不变。
每次评测都用同一份考卷,分数才可以横向比较——今天改了代码,跑一次;上周的
分数存在基线文件里,一对比就知道是进步还是退步。

TeachX 的评测集结构(学习版,够用就好):

```json
{
  "documents": [{"filename": "行列式.md", "content": "..."}],
  "queries": [
    {"query": "行列式的几何意义是什么?", "gold": "体积缩放因子"}
  ]
}
```

**标注技巧:gold 记"关键句"而不是"片段编号"。** 检索到的片段只要包含
这个关键句就算命中。为什么不标片段 id?因为切块逻辑一改,片段编号全变,
标注就作废了;关键句跟着内容走,切块怎么变都有效。

## 二、三个指标:一个比一个严格

用一道题讲清楚:正确片段是第 11 号,检索返回 [10, **11**, 12]。

| 指标 | 问的问题 | 本题得分 |
| --- | --- | --- |
| **Hit@3** | 前 3 条里**有没有**答案 | 1.0(有就行,及格线) |
| **Recall@3** | 前 3 条里**找全了没有** | 相关片段共 1 个、找到 1 个 → 1.0 |
| **MRR** | 第一条正确答案**排多前** | 排第 2 → 1/2 = 0.5 |

三者分工:

- Hit@K 最宽松,适合做"有没有退步"的警报。
- Recall@K 在答案分布在多个片段时才和 Hit 拉开差距。
- **MRR 是排序质量的连续度量**——同样是命中,排第 1 和排第 3 对用户体验
  差很多,MRR 能区分它们。面试里重点讲这个。

全部指标的实现都在 `metrics.py`,每个不到 5 行,纯函数、无副作用。

## 三、评测跑的是真实管线,不是模拟

这是本设计最重要的一点:评测调用的是**生产环境同一条代码路径**——

```text
评测命令
→ KnowledgeService.add_document(真实提取 → 真实切块 → 真实 FTS5 + 向量索引)
→ KnowledgeService.search(真实混合检索 + RRF)
→ 指标计算
```

如果评测走简化版管线,测的就是"简化版好不好",不是"产品好不好"。
唯一替换的是 Embedding 用 Mock(hash 哑向量,确定性)——所以当前分数衡量的是
**FTS 主导的混合检索**;E8 换真实 Embedding 时,用同一份评测集重跑,
分数提升就是最好的面试证据。

## 四、跑一次

```bash
cd backend
uv run python -m teachx.evals.run_rag_eval
```

预期输出(2026-10-04 基线):

```text
评测集: rag-retrieval-basics  查询数: 8
------------------------------------------------------------------------
命中  RR=1.00  相关片段 1 个  什么是矩阵的特征值和特征向量?
命中  RR=0.50  相关片段 1 个  怎么求一个矩阵的特征值?
...(共 8 题)
------------------------------------------------------------------------
     hit@3: 1.000
     hit@5: 1.000
  recall@3: 1.000
  recall@5: 1.000
       mrr: 0.688
```

怎么解读:**全部命中(Hit@3=1.0),但只有一半查询把正确片段排在第一位
(MRR=0.688)**——检索"能找到",排序还有优化空间。这就是评测的价值:
它把"感觉还行"变成了"哪里好、哪里还有空间"。

## 五、基线与回归门禁

```bash
# 改代码前:保存当前分数为基线(基线文件进 Git)
uv run python -m teachx.evals.run_rag_eval --save evals/baselines/rag_retrieval.json

# 改代码后:与基线对比
uv run python -m teachx.evals.run_rag_eval --baseline evals/baselines/rag_retrieval.json
```

对比规则(学习版,一条规则):**任一指标下降超过 0.05 → 命令以退出码 1
失败**,并打印退化项。退出码非零意味着它可以直接接进 CI——不过本项目
暂时没接,check.sh 保持快速;真实需要时加一行即可。

为什么留 0.05 容差?小语料(8 题)上一题的得分变动就是 0.125,零容差会
频繁误报;0.05 允许小波动,但挡得住真正的退化。

## 六、自动测试

`backend/tests/test_rag_eval.py`(7 个):

1. 三个指标 + mean 的手算用例(拿固定输入验证公式)。
2. 评测集自检:每条 gold 关键句必须真的出现在语料里(防标注错误)。
3. 端到端评测:跑真实管线,断言 hit@3 ≥ 0.9、mrr ≥ 0.6(底线留余量,
   检索被改坏时变红,正常波动不误报)。
4. 基线对比:检出超容差退化、容忍容差内波动。

运行 `./scripts/check.sh`(测试数量以命令输出为准)。

## 七、当前边界(诚实说明)

- **8 题、5 篇文档的小考卷**:能证明管线工作、能抓回归,不能代表真实用户
  的查询分布。扩大评测集永远是加分项。
- **Mock Embedding**:当前分数衡量 FTS 主导的检索;语义改写型查询(考卷里
  故意少放)需要真实 Embedding 才能拉开——这是 E8 的活,到时候用同一份
  考卷对比提升。
- **只评了检索,没评回答质量**:忠实度(回答是否基于检索内容)、引用正确性
  需要 LLM-as-a-Judge,属于 E6 后半部分。
- 没有接 CI、没有趋势图表——学习版刻意省略,原理讲得清比工具炫重要。

## 七点五、E8:接真实 Embedding 跑对比

评测脚本已参数化,换 Provider 只需一个参数(默认 mock,自动测试永远是 Mock):

```bash
cd backend
# 真实 Embedding 跑分(需要 OPENAI_API_KEY / OPENAI_BASE_URL 指向支持
# embeddings 的平台;模型名用 --embedding-model 覆盖)
uv run python -m teachx.evals.run_rag_eval \
  --embedding-provider openai --embedding-model <平台的嵌入模型名> \
  --save evals/baselines/rag_retrieval-real.json

# 与 Mock 基线对比
uv run python -m teachx.evals.run_rag_eval \
  --embedding-provider openai --embedding-model <平台的嵌入模型名> \
  --baseline evals/baselines/rag_retrieval.json
```

**实测记录(2026-10-04)**:本地唯一可用的 DeepSeek 平台探测结果为
`/embeddings` 返回 404——该平台没有 embeddings 端点(认证本身是通过的)。
结论:DeepSeek 只能当聊天模型,**Embedding 需要另找支持 embeddings 的
OpenAI 兼容平台**(智谱 / 硅基流动 / DashScope / OpenAI 等),配好
`OPENAI_API_KEY` 与 `OPENAI_BASE_URL` 后执行上面的命令即可。

为什么对比有价值:当前 0.688 的 MRR 是"FTS 主导"的成绩——考卷里的查询和
文档共享关键词。真实 Embedding 上线后,语义改写型查询("怎么求缩放倍数"
命中特征值内容)才能被召回,同一份考卷的分数变化就是最直观的验收证据。

## 八、面试问答

### 1. 你怎么证明你的 RAG 检索是好的?

我用固定评测集跑真实检索管线,报告 Hit@3、Recall@3 和 MRR 三个指标:
当前基线是 Hit@3 = 1.0、MRR = 0.688,意味着全部可命中但排序有优化空间。
评测集和基线文件都提交在仓库里,任何人跑同一条命令能得到同样分数。

### 2. 为什么用"关键句子串"做标注,不标片段 id?

片段 id 依赖切块结果,切块参数一改全部标注作废;关键句跟着内容走,对切块
变化免疫。判定"命中"就是片段包含关键句,简单、可解释、不需要人工标注
整个片段。这是小团队低成本标注的常用做法。

### 3. Hit@K 和 MRR 的区别?什么时候更看重 MRR?

Hit@K 只问"前 K 条里有没有",是及格线;MRR 衡量第一条正确答案的排名,
区分"排第一"和"排第三"——对用户来说这两者体验完全不同。做 QA 类检索
(用户看前一两条)时 MRR 更重要;做资料汇总(要把相关片段都捞出来)时
Recall 更重要。

### 4. 你的评测为什么跑真实管线而不是简化的检索函数?

评测简化管线只能证明"简化管线好"。我的评测从 `KnowledgeService.add_document`
到 `search` 走的是和生产完全相同的代码路径,唯一替换的是 Embedding(Mock,
为了不花钱且确定性)。这样测出的分数才对产品有解释力。

### 5. 改了检索代码怎么知道有没有退化?

改动前跑 `--save` 存基线,改动后跑 `--baseline` 对比:任一指标下降超过
0.05 容差,命令以非零退出码失败并列出退化项。退出码语义可以直接接 CI。
容差的存在是因为 8 题的小考卷上一题就是 0.125,零容差会误报。

### 6. 为什么 Mock Embedding 也敢跑评测?

当前考卷的查询和文档共享关键词,FTS 是主要命中来源,Mock 向量只影响 RRF
的融合权重——所以这个分数衡量的是"FTS 主导的混合检索",这个声明本身就是
评测素养的一部分。等换真实 Embedding 时用同一考卷重跑,提升幅度就是
E8 的验收证据。

### 7. 评测集要多大才够?

够它回答你想问的问题就行。我的目标是"证明管线工作 + 抓住回归",8 题
配底线断言已经做到;要回答"对真实用户够不够好",才需要几十上百题、
并按难度分层。工程上先小后大,每道题都要有人写标准答案,成本是线性的。

### 8. 如果分数突然掉了很多,你怎么排查?

评测输出每题的得分,先看是哪些题掉了;再看这些题命中的片段内容,区分
"没检到"(FTS/向量问题)和"检到但排后"(RRF/打分问题);最后二分最近的
改动。因为评测是确定性的,可以稳定复现任何一次退化——这就是固定考卷
相对"随手试两句"的根本优势。
