# 06：认证与权限

## 先区分认证和授权

这两个词很像，但解决的问题不同。

### 认证 Authentication

回答：

```text
你是谁？
```

例如：

- 用户输入用户名和密码。
- 后端确认账号存在且密码正确。
- 浏览器获得登录凭证。

### 授权 Authorization

回答：

```text
你能做什么？
```

例如：

- 普通用户不能打开管理员后台。
- 用户 A 不能读取用户 B 的会话。
- 只有管理员可以修改全局模型配置。

TeachX 当前完成了认证基础，以及“会话按用户隔离”的第一层授权。

## 为什么不能把密码明文保存

假设数据库被泄露：

```text
admin@example.com | password123
```

攻击者可以直接登录所有账号。

因此密码要做单向哈希：

```text
password123
→ $2b$12$...
```

哈希不能反推出原始密码。登录时不是比较明文，而是用同样算法验证：

```python
bcrypt.checkpw(password.encode(), stored_hash.encode())
```

TeachX 使用 bcrypt：

```text
backend/src/teachx/auth/service.py
```

bcrypt 会故意消耗一定计算时间，让攻击者难以高速猜测密码。

## 为什么不把登录状态放在 localStorage

如果 JWT 放在 `localStorage`，任意 JavaScript 都能读取。  
一旦页面出现 XSS，攻击者可以直接拿走 Token。

TeachX 使用 HttpOnly Cookie：

```python
response.set_cookie(
    key="dt_token",
    value=token,
    httponly=True,
    samesite="lax",
    secure=settings.auth_cookie_secure,
)
```

它的特点：

- JavaScript 不能直接读取。
- 浏览器请求会自动携带。
- `SameSite=Lax` 降低跨站请求伪造风险。
- HTTPS 部署时设置 `secure=True`。

## JWT 是什么

JWT 通常是三段字符串：

```text
header.payload.signature
```

Payload 可以包含：

```json
{
  "sub": "user-id",
  "username": "student@example.com",
  "role": "admin",
  "exp": 1790000000
}
```

注意：JWT Payload 不是加密内容，不能放密码、API Key 等秘密。

TeachX 只存：

- 用户 ID
- 用户名
- 角色
- 签发时间和过期时间

签名使用 `TEACHX_AUTH_SECRET`。生产环境的 Secret 至少需要 32 个随机字节。

## 注册流程

```text
浏览器提交用户名和密码
→ 后端校验格式
→ bcrypt 生成密码哈希
→ 写入 users 表
→ 第一个用户获得 admin 角色
```

第一个用户成为管理员，是因为新部署的系统还没有管理员。后续用户默认是普通用户。

## 登录流程

```text
浏览器提交用户名和密码
→ 查询 users 表
→ bcrypt 验证密码
→ 生成 JWT
→ 写入 HttpOnly Cookie
→ 返回 authenticated=true
```

如果用户不存在，后端仍然执行一次 dummy bcrypt 校验，避免通过响应时间推测账号是否存在。

## FastAPI 如何保护接口

认证依赖在：

```text
backend/src/teachx/api/auth_dependencies.py
```

接口只需要声明：

```python
user: UserRecord = Depends(require_user)
```

逻辑是：

1. 如果认证关闭，返回本地开发用户。
2. 如果认证开启，读取 Cookie。
3. 验证 JWT。
4. 查询用户是否仍然存在。
5. 无有效用户时返回 401。

`sessions` 和 `knowledge-bases` 路由现在都经过这一层。

## WebSocket 如何鉴权

WebSocket 不能使用普通 HTTP 401 流程，因此在建立连接前检查 Cookie：

```python
user = await container.auth.user_from_token(token)
if user is None:
    await websocket.close(code=4401)
```

只有通过验证后，才调用 `websocket.accept()`。

AgentRuntime 会把用户 ID 传给 SessionRepository：

```python
runtime.run_turn(command, user_id=user.id)
```

因此后续查询和新增会话都绑定到当前用户。

## 会话隔离

`messages` 表属于 `sessions` 表。  
只要严格限制用户能访问的 `session_id`，就同时保护了消息内容。

会话查询增加条件：

```sql
WHERE s.id = ?
  AND (? = '' OR s.user_id = ?)
```

认证关闭时 `user_id` 为空，保持单用户开发体验。  
认证开启时，用户只能列出和读取自己的会话。

## 如何启用认证

后端：

```bash
TEACHX_AUTH_ENABLED=true
TEACHX_AUTH_SECRET=至少32字节随机字符串
TEACHX_AUTH_COOKIE_SECURE=false
```

前端：

```bash
NEXT_PUBLIC_AUTH_ENABLED=true
```

本地 HTTP 开发使用 `COOKIE_SECURE=false`。  
正式 HTTPS 部署必须改为 `true`。

## 常见误区

### “JWT 可以自动让接口安全”

不会。接口仍要验证签名、检查过期时间，并检查用户是否仍存在。

### “前端隐藏按钮就是授权”

隐藏按钮只是界面行为。攻击者可以直接调用 HTTP 或 WebSocket 接口，权限必须由后端执行。

### “密码哈希后可以解密找回”

不能。正确的密码找回流程是重置密码，而不是解密原密码。

### “认证开启后所有数据自动隔离”

不会。每张业务表都需要明确所有权规则。TeachX 已经完成会话隔离，知识库所有权隔离将在下一步继续实现。
