# 26：端到端 Agent 评测——怎么知道"整个助手"真的能用

> 本章适合第一次接触"任务级评测"和"LLM-as-a-Judge"的读者。读完后，你将能够：
> 说清楚 TeachX 的三层评测体系各自评什么；跑通任务级考卷并看懂断言输出；
> 解释为什么 Judge 不能进 CI；复述真实验证中抓到的"推理模型吞掉输出预算"
> 故事——那是面试里最有说服力的一段。

## 为什么需要它

到教程 25 为止，TeachX 已经有两层评测，但各管一段：

- 检索评测（教程 22）只评**检索环节**：给定查询，能不能召回对的片段。
- 意图评测（教程 25）只评**识别环节**：给定消息，分类对不对。

中间最大的空白是**整个回合**：用户说了一句话，路由、提示词、模型、工具、
裁剪、存储全部串起来之后——行为对不对？该调的工具调了吗？不该调的调了吗？
回答里有用户要的东西吗？检索评测的 Hit@3=1.0 不能回答这些问题，单元测试
（每个都只测一条缝）也不能。

P1 补上第三层：**任务级评测**。每个用例是一条真实用户输入 + 一组期望行为
断言，Mock 模型全链路确定性执行，进 check 门禁；再配一个小样本
LLM-as-a-Judge（让模型给回答的忠实度和有用性打分）手动验证真实模型。

## 操作步骤

### 1. 跑任务级考卷，看懂输出

```bash
cd backend && uv run python -m teachx.evals.run_agent_eval
```

每行是一个任务：`✓/✗` + 任务 id + 实际调用过的工具。考卷在
`backend/evals/datasets/agent_tasks.json`，7 个任务覆盖六个意图各一次，

把数据集里 `calc-basic` 的 `answer_contains` 临时改成 `["999"]` 再跑：

```text

  断言 answer_contains 失败: 期望 回答包含 '999'  实际 计算结果已经得到：96。
```

失败时逐条打印"期望 vs 实际"，并自动调回合 trace 分析器（教程 23）把问题


直接拒绝运行。确认要花额度时加 `--yes`（本地 `.env` 配了真实模型即可）：

## 它是怎么工作的

### 断言 schema：评测集长什么样

每个任务 = 输入 + 期望，`expect` 字段是一张白名单（写错字段名直接报错，
不静默忽略）：

| 断言 | 检查什么 | 从哪取证据 |
| --- | --- | --- |
| `status` | 回合正常结束 | done 事件 metadata |
| `intent` / `agent` / `intent_detector` | 路由正确（P0 的字段在这里变现） | done 事件 metadata |
| `must_call_tools` | 必调的工具都调了 | tool_result 事件 |
| `forbidden_tools` | 禁止的工具一个都没执行（最小权限） | tool_result 事件 |
| `answer_contains` / `answer_not_contains` | 回答内容要点 | result 事件正文 |
| `min_sources` | 引用条数下限 | sources 事件 |

7 个任务的覆盖设计：计算（工具执行 + 数值正确）、练习（路由 + 禁检索 +
回答是题）、进度（零工具只读）、检索命中（引用 ≥1）、带库讲概念、无库讲
概念（检索工具根本不提供）、闲聊兜底。

### 两层执行：为什么 Mock 是门禁、Judge 只能手动

**Mock 层是回归门禁。** Mock 模型是确定性规则：同样的输入永远同样的输出，
考卷任何人任何机器跑出同一结果，零额度，可以放进 `check.sh` 每次都跑。
它验证的是**系统的行为契约**——路由、权限、工具、内容要点。

**Judge 层只能手动。** 三个原因：每次运行花真钱；真实模型输出每次不同，
分数不可复现，当门禁会随机误伤；评审模型自己也会看走眼。所以 Judge 是
"定期体检"：报告存 `evals/reports/`（gitignore），供人工对比留档，脚本
里有两道保险——Mock Provider 直接拒绝运行、必须显式 `--yes` 才消费额度。

### 失败归因：从"挂了"到"挂在哪层"

任务失败时，执行器把这个任务持久化的事件流喂给 `turn_trace.analyze_turn_events`
（E6b 的纯函数分析器），打印五层归因。这一步把三层评测串成闭环：检索评测
管召回、意图评测管分类、任务评测管全程，而 trace 管"坏了之后往哪看"。

### 真实验证抓到的两个问题（这也是评测价值的证明）

1. **推理模型吞掉输出预算。** 首次真实 Judge 运行时，practice 和 progress
   两个任务的回答是**空的**，但回合状态是 completed。查 usage 明细：
   `agent_loop_round` 消耗了整整 1024 completion tokens——deepseek-flash
   是推理模型，把默认输出预算全部花在思考内容上，正文一个字没生成就被
   `max_output_tokens` 截断。运行时"诚实"地返回了空字符串，但把空回答
   伪装成 completed 违反 E5 的诚实失败契约。修复：新增第四个诚实失败码
   `output_truncated`（`finish_reason == "length"` 且无可见内容时，回合
   状态 failed、可重试，trace 归因到模型层），并把使用推理模型的输出预算
   建议提高到 4096。
2. **评审自己也被截断过。** 给评审调用的输出预算最初只有 128 tokens，
   推理模型光思考就超了，JSON 没生成就断——两个任务"解析失败"。提高到
   1024 后 3/3 解析成功。同一根因在两处出现，这正是"预算意识"要写进
   直觉的证据。

顺带一提，真实运行里还观察到 deepseek-flash 在不配工具的子 agent 上会把
**工具调用的原始标记当正文吐出来**（DSML 文本泄漏），评审据此给了练习任务
有用性 1 分。这是模型侧产物，运行时不解析它；记录在此，避免后来者以为是
自己的代码坏了。

## 常见错误

| 现象 | 原因 | 处理方式 |
| --- | --- | --- |
| `评测失败: N 个任务未通过断言` | 改动了路由、工具策略或 Mock 行为 | 看每条"期望 vs 实际"；是行为退化就修代码，是有意的行为变更就同步改考卷并说明 |
| Judge 提示 `当前 Provider 是 mock` | 未配置真实模型就加了 `--yes` | 配置 `TEACHX_LLM_PROVIDER=openai` 与 Key；或明确这就是要拒绝的场景 |
| Judge 大量"评审输出解析失败" | 评审输出预算太小,推理 token 挤掉了 JSON | 确认脚本用 1024;自定义更小预算前先想清楚推理模型的开销 |
| 真实模型回合回答为空但 completed | 旧版本行为;当前版本会报 `output_truncated` | 升级后重试;仍空则检查模型是否推理型,调大 `TEACHX_MAX_OUTPUT_TOKENS` |
| 改了数据集结构后评测直接抛异常 | `expect` 写了白名单外的字段 | 按报错字段名修正;这是防止断言悄悄失效的机制 |

## 当前边界

- **7 个任务偏小。** 它是回归门禁不是产品验收,扩大覆盖（多轮对话、附件、
  预算回退路径的任务化）是低成本演进方向。
- **Mock 门禁校准于 Mock 行为。** `answer_contains` 里的关键词按 Mock 的
  确定性输出挑的;真实模型不保证命中——真实质量归 Judge 层管,两层各司其职。
- **Judge 是单评审、单次打分。** 没有多评审交叉、没有重试投票;分数噪声
  （±1 很常见）靠人工复核消化,报告只是留档不是结论。
- **报告不进 Git。** `evals/reports/` 已 gitignore;教程里引用的数字来自
  2026-10-06 的一次运行,复跑数字会不同（模型输出不可复现）。
- **DSML 泄漏未处理。** 模型侧产物,运行时不解析、不清洗;如果未来换主模型
  后仍出现,再考虑内容侧过滤。

## 面试问答

**Q1：单元测试已经很全了（146 个），为什么还要任务级评测？**

单元测试验证"每条缝是对的"：重试对、幂等对、路由对。但用户经历的是整条
链路的**组合行为**——组合可能出新问题（本次真实验证里"零工具子 agent 的
空回答"就是组合层现象,单测全绿也发现不了）。任务级评测用最小成本补这个
缺口：考卷就是几条用户输入加断言,跑在真实 AgentRuntime 上,既当测试又当
文档。三层分工：单测管缝、任务考卷管链路、Judge 管体验质量。

**Q2：断言 `forbidden_tools` 为什么看 tool_result 而不是看给模型的工具
清单？**

产品承诺是"练习意图不会发生检索",真正要管的是**执行**这个副作用。工具
清单只是手段——清单里没有,模型通常不会调;但提示词注入或幻觉仍可能让它
调,这时执行层拦截会让调用以失败告终（`tool_not_allowed`）,同样不会产生
检索结果。断言盯在执行结果上,测的是承诺本身而不是实现细节,实现怎么改
（拦截策略、schema 裁剪）考卷都不用动。

**Q3：为什么 Mock 层进 CI、Judge 不进?权衡了什么?**

CI 的生命线是**可复现**：红灯必须意味着"代码坏了"而不是"模型今天心情不
好"。Mock 输出确定、零成本,天然满足;真实模型输出随机、要花钱,放进 CI
会制造随机红灯 + 烧预算,还会激励团队跳过评测。所以 Judge 定位成手动体检:
加两道保险（Mock 拒跑、`--yes` 确认）,报告 gitignore（不可复现的东西不能
当基线）,数字只进文档并标注日期。这个"确定性进门禁、随机性进报告"的
分界是评测体系设计的核心取舍。

**Q4：讲讲你们评测真实抓到的 bug,以及它怎么影响设计。**

首跑真实 Judge,两个任务回答为空但状态 completed。查 usage 明细发现模型
一轮消耗了恰好 1024（等于输出上限）completion tokens——推理模型把预算全
花在思考上,正文没生成就被截断。这暴露两件事:一是空回答伪装 completed
违反我们自己的诚实失败契约,于是新增 `output_truncated` 失败码（与
turn_timeout 同一套机制:failed + retryable + trace 归因模型层）;二是
默认输出预算对推理模型太小,文档明确建议 4096。更有意思的是评审调用自己
也栽在同一坑（128 tokens 评审预算被思考吃光）,同一根因出现两次——现在
"给推理模型留思考余量"是团队的默认直觉了。

**Q5：`answer_contains` 这种关键词断言会不会太脆弱？真实模型换个说法就挂。**

会,所以这层考卷故意只跑 Mock。关键词断言在确定性模型上是精确的回归探针;
对真实模型它确实脆弱,所以真实质量交给 Judge 的 1~5 分（语义层面的"有没有
讲到点子上"）。如果未来想让任务考卷直接跑真实模型,正确升级路径是把
`answer_contains` 换成"要点清单 + Judge 判定覆盖数",而不是往考卷里堆
同义词——那是把脆弱性从断言挪进数据,不会消失。

**Q6：Judge 用同一个模型既当选手又当裁判,不会有偏吗？**

会有自评偏置（模型倾向给自己风格的输出高分）,这是已知限制。学习版的
缓解是:评分细则锚定在可核查的事实上（忠实度问"是否基于资料、有没有编造",
不是"写得好不好"）;分数只做人工复核的线索,报告里的 reason（一句话理由）
比分数更重要——人看理由判断评审是否靠谱。升级路径:换异构评审模型、
同一回答多次评审取中位数、关键任务双人评审。都是加配置不加框架的事。

**Q7：失败归因为什么复用 E6b 的 trace 分析器,而不是给评测单独写一套？**

因为数据同源:任务评测的执行器跑的就是生产 AgentRuntime,事件流格式和线
上一模一样,trace 分析器本来就是吃这份事件流的纯函数。单独再写一套意味着
两种归因逻辑会漂移——评测说挂在工具层、线上诊断说挂在模型层,信谁?复用
还免费得到一致性测试:任务失败路径每次跑 check 都在给 trace 分析器做真实
数据的集成验证。

**Q8：这套评测离"生产级评测平台"差什么？**

按差距从小到大:一是数据量与来源（7 条手写 → 线上流量抽样 + 人工标注,
并且把线上坏例反哺进考卷）;二是持续执行（进 CI 是每日跑,还要有趋势看板
而不是单次报告）;三是真实模型的回归策略（固定模型版本快照 + 分数容差带,
或只对比不卡门禁）;四是 Judge 的统计化（多评审、置信区间）。框架和管线
已经把这些位置的接口留好了——数据集是 JSON、执行器是纯函数、报告是结构化
JSON——补的是运营不是架构。

**Q9：为什么把"输出截断"定义成回合失败,而不是把思考内容展示给用户？**

思考内容是模型的中间过程,展示它等于把内部推理当产品输出——格式不可控、
可能包含自我矛盾,还会教坏用户"这就是答案"。产品契约是"回答要么完整、
要么诚实地说失败并保留已生成的部分"。截断时正文为空,没有任何可保留的
部分,所以正确的语义是 failed + retryable,并告诉用户两条出路:重试,或调大
输出预算。这也是 E5 诚实失败契约的延伸检验——新失败模式出现时,先问
"对用户最诚实的表达是什么",再问"代码往哪改"。

## 自测题

1. 三层评测（检索/意图/任务）各评什么?一条用户消息从进来到回答,每一层
   分别在哪个环节给它打分?
2. `forbidden_tools` 断言读的是哪类事件?为什么这样设计?如果执行层拦截
   了被禁工具,事件流里会出现什么,断言会过还是挂?
3. Judge 为什么必须有两道保险（Mock 拒跑、`--yes`）?去掉哪一道会发生
   什么具体事故?
4. `output_truncated` 的判定条件是哪两个?为什么"有部分正文 + finish=length"
   不走这个失败路径?
5. 如果把任务考卷直接拿去跑真实模型,哪些任务最可能挂?挂了该改考卷、
   改代码,还是换一层评测来管?
