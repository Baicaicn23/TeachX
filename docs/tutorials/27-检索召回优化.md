# 27：检索召回优化——先找到根因，再动手改

> 本章适合第一次接触"检索召回优化"（Retrieval Recall Optimization）的读者。
> 读完后，你将能够：说出 TeachX 检索质量差的真正根因（不是参数、不是模型，
> 是中文分词）；解释 trigram 分词器为什么能救中文检索；跑通"改写—扫参—回退"
> 三步优化并看懂每步的量化证据；回答面试官关于"如何系统性地优化召回"的追问。

## 为什么需要它

P2 开始前，TeachX 的检索考卷是这样的成绩：关键词卷（8 题）MRR 0.688，
语义卷（6 题，学习者口语提问）MRR 0.639。能命中（hit@3=1.0），但正确答案
经常排在第 2、3 位。按路线图，这一阶段的任务是"查询改写 → 召回参数调优 →
空结果回退，每步量化"。

但动手后的第一个发现改变了整个计划：**调参数没有用，因为根因不在参数——
FTS5 的默认分词器根本不切中文**。本章如实记录这个"先诊断、后开方"的过程，
因为排查路径本身就是面试里最值钱的部分。

## 最终结果

```bash
cd backend
uv run python -m teachx.evals.run_rag_eval --baseline evals/baselines/rag_retrieval.json
```

预期（优化后）：

```text
     hit@3: 1.000
       mrr: 0.938        ← 优化前 0.688
回归检测:与基线相比无退化

# 语义卷(学习者口语考卷)
       mrr: 1.000        ← 优化前 0.639
```

关键词卷 MRR **0.688 → 0.938**（+0.25），语义卷 **0.639 → 1.000**
（+0.361），全量检查 153 passed。

## 前置条件

- 已能运行 `./scripts/check.sh` 和检索评测（教程 22）。
- 理解两个词：
  - **召回（recall）**：该找到的资料有没有被找回来。找不全，后面的大模型
    再聪明也回答不了——这就是"检索不全怎么优化"要解决的问题。
  - **分词器（tokenizer）**：全文索引把文本切成"词"存储的规则。检索就是
    拿查询的词去索引里对号——两边切法对不上，就永远查不到。

## 它是怎么工作的：根因诊断（第一步其实是测量）

按路线图本该直接做"查询改写"，但写扩写表之前先做了一次通道级诊断：
把一条语义卷查询分别喂给 FTS 通道和向量通道，看各自把正确答案排在第几。
这一看发现了大问题：

```text
FTS5 MATCH '"特征值"'  → 0 行
FTS5 MATCH '"正态分布"' → 0 行
```

**全文索引对中文词一个都查不到。** 原因：FTS5 默认的 unicode61 分词器按
空格和标点切词，**一整段连续中文是一个 token**——语料 token 是
"实对称矩阵的重要性质"这样的长串，查询词"特征值"永远对不上号。这意味着：

- bm25 排序从未真正工作过（没有匹配就没有排序）；
- 中文检索实际靠两条兜底在撑：FTS 内置的 LIKE 子串兜底（**无排序**，
  按插入顺序返回）和向量通道；
- 此前考卷的"能命中"几乎全是向量通道的功劳。

### 修复：trigram 分词器 + 重建迁移

FTS5 原生支持 `tokenize='trigram'`：以 3 个字符为滑窗切词，中文子串检索
和 bm25 排序原生可用。改动两处：

1. `storage/database.py`：新库 DDL 直接用 trigram；旧库在 `initialize()`
   里自动检测旧分词器并**整表重建**（tokenizer 无法 ALTER，只能从
   `knowledge_chunks` 重灌索引），幂等——重建后检测即通过。
2. `knowledge/service.py`：查询词从中文 2-gram 滑窗改为 **3-gram**
   （trigram 要求 MATCH 词串不少于 3 个字符；2 字短词交给 LIKE 兜底）。

### 第二步：查询改写（同义词表）

修好分词后，词汇通道活了，"学习者口语 vs 语料术语"的词汇鸿沟才显出来
（"一模一样"vs 对称矩阵、"表出来"vs 线性组合）。`knowledge/query_rewrite.py`
维护一张人工同义词表，**把术语追加到查询后**（不替换原词），纯函数、
零成本、可开关（`expand_synonyms`）。

关键教训：扩写表第一版效果是零——不是没生效，而是当时 FTS 还是坏的，
扩写词根本进不了排序。**先修通道，优化才有意义。** 分词修好后，同一张
表直接把语义卷从 0.833 推到 1.000。

### 第三步：扫参（诚实的"参数不敏感"结论）

`rrf_k`（RRF 融合常数）和 `recall_depth`（每路召回深度倍数）暴露为服务
参数和评测 CLI 开关，9 种组合扫了一遍：**在当前考卷规模下全部结果相同**
（MRR 0.938 / 1.000）。结论如实记录：考卷是 5 篇文档的小语料，参数不敏感；
参数保留为可配置，是为更大的真实知识库预留，不为刷分。

### 第四步：空结果回退（跨库扩大范围）

选中的知识库里，词汇通道（FTS）一个片段都没命中时，自动扩大到**同一用户
的其他知识库**再检索一次（owner 边界不变，不越权），命中片段标记
`widened_bases=True`，agent 工具和搜索 API 都会如实告知"这来自扩大范围"。

触发条件只看 FTS 是刻意的：向量相似度哪怕在完全无关的语料上也常有噪声
高分，不能当"资料存在"的证据——这是 API 验证阶段抓到的设计缺口（第一版
"融合结果为空才回退"被向量噪声挡住了，从不触发）。

## 量化证据（每一步）

| 配置 | 关键词卷 MRR | 语义卷 MRR |
| --- | --- | --- |
| P2 前（unicode61 + 2-gram + 无扩写） | 0.688 | 0.639 |
| + trigram 分词（无扩写） | 0.938 | 0.833 |
| + trigram + 同义词扩写（最终配置） | **0.938** | **1.000** |

- 扩写单独看：修分词前 +0.000（通道坏了），修分词后语义卷 +0.167。
- 扫参：9 组合无差异（小语料参数不敏感，如实记录）。
- 回退：考卷查询全部有命中，不触发回退，两卷分数不变（无回归）；
  行为由 7 个新单元测试覆盖（含越权防护）。

## 常见错误

| 现象 | 原因 | 处理方式 |
| --- | --- | --- |
| 旧库启动变慢一次 | trigram 重建迁移在重灌索引 | 一次性开销；数据量大时可关注日志,重建后即恢复 |
| 扩写开关关了分数也不变 | 你在 trigram 之前的老版本上测 | 拉最新代码；分词修复是扩写生效的前提 |
| 2 个字的词搜不到（FTS 通道） | trigram 要求 MATCH 词串 ≥3 字符 | 属已知边界；2 字词走 LIKE 兜底（无排序）和向量通道 |
| 扩大范围的结果"不是选中库的" | 这是回退功能本身 | 工具与 API 都带 `widened_bases` 标记;不想要可只建单个知识库 |
| 改了 `query_rewrite.py` 后 check 变红 | 同义词表改坏导致考卷回归 | 跑检索评测看逐题 RR;改动需同时过两份考卷的基线门禁 |

## 当前边界

- **语义卷满分不代表语义检索完美。** 考卷只有 6 题、语料 5 篇；mock 向量
  是字符哈希。真实语义向量的对比（智谱 embedding-3）需要用户 Key 手动跑
  （方法同教程 22 的 E8 章节），预期语义卷仍有区分度。
- **2 字中文词进不了 FTS 通道。** trigram 的硬约束；LIKE 兜底无排序。
  如果真实使用中 2 字词查询占比高，可考虑补偿策略（扩写表里为常用 2 字词
  配 3 字同义术语）。
- **同义词表是人工的。** 只覆盖线性代数等已见场景；换学科需要补表或上
  LLM 改写（接口已预留：`expand_query(query) -> str` 可整体替换为实现）。
- **扫参结论只适用于小语料。** 大知识库下 rrf_k/depth 的最优值可能不同,
  参数已暴露为可配置，换规模后应重新扫。
- **跨库回退只到"同用户全部库"。** 不跨用户（权限边界），也不做"全平台
  公共知识"（产品里没有这个概念）。

## 面试问答

**Q1：你们检索优化的根因是什么？怎么找到的？**

不是参数也不是模型，是**中文分词**：FTS5 默认 unicode61 分词器不切中文，
一整段中文是索引里的一个超长 token，查询词永远匹配不上，bm25 排序从未
工作过，中文检索一直靠 LIKE 兜底（无排序）和向量通道在撑。找到它的方法
是通道级诊断：怀疑参数之前，先分通道看"正确答案在各通道里排第几"，于是
直接观察到 `MATCH '"特征值"'` 返回零行。教训：优化之前先让测量告诉你
问题在哪一层，否则扩写表写了也是零效果（我们真的先踩了这个）。

**Q2：为什么选 trigram 分词器？ alternatives 有哪些？**

候选有三：换 ICU 分词器（SQLite 标准版不带，要编译扩展）；应用层分词
（jieba 切词后入库,但查询侧也要分词,两套词表要保持一致,还要自建排序）；
trigram（SQLite ≥3.34 原生,3 字符滑窗,子串匹配 + bm25 开箱即用）。选
trigram 因为它零依赖、原生排序、对"子串即语义"的中文最合适;代价是 MATCH
词串必须 ≥3 字符,2 字词进不了 FTS 通道（LIKE 兜底 + 向量通道补偿）。
学习版优先零依赖方案,并把代价如实写进边界。

**Q3：tokenizer 改不了配置,存量数据库怎么办？**

tokenizer 是建表参数,SQLite 不支持 ALTER,只能整表重建。迁移做成幂等的
自动迁移:启动时读 `sqlite_master` 里这张虚拟表的建表语句,发现不是 trigram
就 DROP 后按 `knowledge_chunks` 业务表重灌索引（业务数据零丢失,索引只是
派生物）。重建后检测自然通过,迁移只执行一次。这是"索引是派生数据"的
经典好处:派生物可以随时按权威数据重建。

**Q4：查询扩写为什么是"追加"而不是"替换"？为什么第一版零效果？**

追加保证原查询的关键词信息不丢——扩写词是猜的,原词是用户给的,猜错不能
覆盖真值。第一版零效果的原因很有教育意义:当时 FTS 通道是坏的,扩写词
进了一个不工作的排序器;修好分词后,同一张表把语义卷从 0.833 推到 1.000。
这是"优化依赖被优化对象健康"的活例子——所以本章把诊断放在扩写之前讲。

**Q5：扫参发现参数完全不敏感,这算优化失败吗？**

不算,这是测量带来的确定性知识。扫参前我们不知道 rrf_k/depth 是否影响
这个系统;扫完后我们**知道**在当前规模下不敏感,默认值可以放心保留,把
注意力留给真正有效的杠杆（分词、扩写）。参数保留为可配置,是为真实规模
的知识库预留——考卷涨了、语料大了,重新扫一遍即可,CLI 开关都是现成的。
"诚实的无效结论"比"编造的收益"对工程更有价值。

**Q6：空结果回退的触发条件为什么只看 FTS 通道,不看融合结果是否为空？**

第一版用的就是"融合结果为空才回退",API 验证时发现从不触发:向量通道的
余弦相似度在完全无关的语料上也常有噪声分（尤其 mock 哈希向量）,一个噪声
命中就把回退挡住了。改成"FTS 通道零命中才回退"——词汇层完全对不上号才是
"这个库里没有这份资料"的可靠信号。这体现一个检索工程原则:**不同通道的
"空"含义不同,词汇空是证据,语义低分不是。**同时回退结果全部带
`widened_bases` 标记,工具和 API 都如实告诉调用方"这来自扩大范围"。

**Q7：跨库回退会不会造成信息泄漏或越权？**

不会,有三层约束:回退范围是"当前用户的全部知识库",`list_bases` 按
owner_id 过滤（管理员除外,与既有权限模型一致）;单元测试里有专门的越权
用例（用户 A 选中的库未命中时,用户 B 的库绝不出现）;回退只发生在检索
层面,引用和来源信息照常携带原知识库名,模型和用户都能看到答案来自哪。
设计上的取舍是"便利性换透明性":扩大范围可以,但必须标注。

**Q8：如果语料换成了英文为主,这套优化还成立吗？**

分词修复对英文无感（unicode61 本来就能切英文）,trigram 对英文子串匹配
同样有效,所以不会变差;扩写表是中文口语专属,对英文是空操作（模式匹配
不上）,需要换一张英文口语表或 LLM 改写;回退逻辑语言无关。架构上的准备
是"改写函数是单一接缝"——`expand_query(query) -> str`,换语言或换 LLM
实现都不动检索管线。多语言语料混合时 trigram 依然成立（按字符滑窗,
语言无关）。

**Q9：为什么语义卷能到 1.000,你却说不代表语义检索完美？**

因为语义卷只有 6 题、语料只有 5 篇,而且是 mock 哈希向量（字符级信号,
不是真语义）。满分说明"这 6 个口语说法在这份小语料上被这三步优化救活
了",不说明系统具备通用的语义检索能力。真正语义能力的度量要用真实
embedding 跑同一份考卷（E8 已建立方法:智谱 embedding-3,语义卷就是为此
设计的）,并把语料和题目扩到统计上有意义的规模。声明边界不是谦虚,是
防止下一次决策（比如"检索已经满分了不用做 Reranker"）建立在假信号上。

**Q10：如果要用 LLM 做查询改写,怎么接？怎么量化？成本怎么控？**

接法:`expand_query` 是单一接缝,在 service 层加一个可选的 LLM rewriter,
规则表结果作为 LLM 不可用时的回退——和意图识别（教程 25）的"规则兜底 +
LLM 增强"同一个模式。量化:同一套考卷,开关 A/B 对比 MRR/Hit,规则版分数
就是 LLM 版不得击穿的下限。成本:LLM 改写是每次检索多一次低 token 调用,
可以只在 FTS 零命中或低置信时触发（按需改写）,或者只在向量通道无果后
进入回退路径时改写——先便宜后昂贵,与空结果回退天然组成一个成本梯度。
