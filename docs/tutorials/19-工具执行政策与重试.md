# 19：工具执行政策、重试、幂等与参数脱敏

> 本章适合第一次接触工具调用、重试和幂等机制的读者。读完后，你应该能够解释：
> 为什么不能所有错误都重试，什么是有限重试，生产 Agent 如何观察一次工具调用，
> 如何用幂等键保证有副作用的工具不被重复执行，以及敏感参数如何脱敏。

## 这一章解决什么问题

之前的工具调用只有一条简单路径：

```text
模型请求工具
→ ToolRegistry.execute()
→ 工具执行一次
→ 成功或失败
```

这会产生几个问题：

- 数据库短暂锁住时，本来重试一次就能成功，却直接失败。
- 参数写错时，如果无脑重试，只是重复浪费三次。
- 工具一直不返回时，整个 Agent 回合会一直卡住。
- 前端只知道“失败”，不知道尝试了几次、是否超时、错误是否可重试。

E1 把工具执行升级为：

```text
模型请求工具
→ 读取工具自己的执行政策
→ 判断错误是临时还是永久
→ 临时错误执行有限退避重试
→ 每次执行都有超时上限
→ 返回尝试次数、重试次数、耗时和错误码
```

## 用户场景

用户提问时，知识库正在被另一个写入操作短暂占用。SQLite 返回：

```text
database is locked
```

这不是用户的问题，也不是模型参数错误，而是临时资源冲突。

TeachX 的处理结果是：

```text
第 1 次：数据库 locked，失败
→ 等待退避时间
第 2 次：检索成功
→ Agent 继续回答，用户甚至不需要知道发生过重试
```

另一个场景是计算器参数无效：

```text
expression = "__import__('os').system('whoami')"
```

这是永久性参数错误，重试三次仍然会失败，所以必须立即停止。

## 一、错误必须分类

“重试”最危险的实现方式是：

```python
except Exception:
    retry()
```

它会把参数错误、权限错误、代码 Bug、数据库锁定和网络抖动全部当成同一种问题。

TeachX 现在分成三类：

| 类型 | 含义 | 是否重试 | 例子 |
| --- | --- | --- | --- |
| `ToolError` | 永久性业务或参数错误 | 否 | 表达式非法、参数缺失 |
| `ToolTransientError` | 临时失败，重复请求有机会成功 | 是 | 数据库 locked、外部服务短暂不可用 |
| `ToolTimeoutError` | 单次执行超过时间上限 | 是，完成次数受限 | 知识库查询长时间无响应 |

代码位置：

```text
backend/src/teachx/runtime/tools.py
```

核心接口：

```python
class ToolError(ValueError):
    code = "tool_error"


class ToolTransientError(RuntimeError):
    code = "tool_transient_error"


class ToolTimeoutError(ToolTransientError):
    code = "tool_timeout"
```

面试里可以用一句话解释：

> 重试策略的前提不是“失败了”，而是“这个失败是否具有恢复可能，并且重复执行是否安全”。

## 二、工具自己声明执行政策

不同工具不应该共用同一套策略。

计算器是纯函数，结果确定，没有网络和数据库，不需要重试；知识库搜索依赖 SQLite，存在短暂锁竞争。

因此新增 `ToolPolicy`：

```python
@dataclass(frozen=True, slots=True)
class ToolPolicy:
    read_only: bool = True
    max_attempts: int | None = None
    timeout_seconds: float | None = None
    retry_base_delay_seconds: float | None = None
    retry_max_delay_seconds: float | None = None
```

`None` 表示继承 `ToolRegistry` 的默认值。

当前工具政策：

```python
# CalculatorTool
policy = ToolPolicy(read_only=True, max_attempts=1, timeout_seconds=2.0)

# KnowledgeSearchTool
policy = ToolPolicy(read_only=True, max_attempts=3, timeout_seconds=10.0)
```

为什么 `read_only` 暂时还没直接参与执行？

它是为后续能力准备的：

- E2 根据是否有副作用决定是否允许重复执行。
- E4 只读工具可以并发的有上限执行，有副作用工具保持串行。

提前把“工具的语义”放在统一接口上，避免以后每个工具单独判断。

## 三、重试放在 ToolRegistry，而不是每个工具里

每个工具如果自己写：

```text
for attempt in range(3)
try/except
sleep
metadata
```

会产生大量重复代码，也很难保证所有工具行为一致。

TeachX 把重试放到 `ToolRegistry.execute()`：

```text
AgentRuntime
→ ToolRegistry.execute()
→ 解析有效政策
→ 循环调用具体工具
→ 返回统一 ToolResult
```

这是一种“深模块”设计：

- 外部接口仍然只有一个 `execute()`。
- 重试、超时、退避、错误分类和元数据都在内部完成。
- Agent Loop 不需要知道工具实现用了数据库还是 HTTP。

面试可以这样回答：

> 我把横切关注点放在 ToolRegistry 这一层，而不是散落到每个工具。调用方只需要知道一次工具执行的结果，不需要理解重试策略。

## 四、有限重试与指数退避

当前退避公式：

```python
delay_seconds = min(
    retry_max_delay_seconds,
    retry_base_delay_seconds * (2 ** (attempt_count - 1)),
)
```

默认配置：

```text
第 1 次失败后等待 200 ms
第 2 次失败后等待 400 ms
第 3 次失败后等待 800 ms
最多等待 2000 ms
```

为什么不能固定 10 ms 连续重试？

- 外部服务可能正在恢复。
- 立刻重试只会继续打满资源。
- 多个请求同时重试会造成“重试风暴”。

生产环境通常还会加入 jitter，也就是随机抖动：

```text
200 ms + random(0 ~ 100 ms)
```

随机化可以避免大量客户端在同一个时间点同时重试。

当前 TeachX 使用确定性退避，方便测试；后续可以在不改变 `ToolRegistry` 接口的情况下加入 jitter。

## 五、超时不是失败重试的替代品

超时解决的是：

```text
工具一直不返回，Agent 回合不能无限等待
```

当前使用：

```python
await asyncio.wait_for(
    tool.execute(context=context, **arguments),
    timeout=policy["timeout_seconds"],
)
```

如果超时，会产生：

```text
error_code = tool_timeout
timed_out = true
retryable = true
```

要注意：`asyncio.wait_for` 会取消等待中的协程，但它无法强制停止一个正在阻塞线程的同步函数。

所以工具内部应优先使用：

- `async` 数据库客户端。
- `httpx.AsyncClient`。
- 异步文件或网络调用。

否则 timeout 可能只是让调用方放弃等待，后台线程仍继续运行。

## 六、尝试次数和耗时必须可观察

成功后，工具返回的 metadata 会包含：

```json
{
  "attempt_count": 2,
  "retry_count": 1,
  "retry_delays_ms": [200],
  "duration_ms": 231.42,
  "read_only": true,
  "max_attempts": 3,
  "timeout_seconds": 10
}
```

失败时还会包含：

```json
{
  "error_code": "tool_timeout",
  "retryable": true,
  "timed_out": true,
  "attempt_count": 3,
  "retry_count": 2
}
```

这些字段会进入 `tool_result` 事件，并持久化在助手消息中。

前端工具轨迹会显示：

```text
attempts  2 (1 retries)
duration  231.42 ms
```

为什么这些字段重要？

- 排查失败到底发生在哪一层。
- 评估工具延迟和重试率。
- 判断是否需要调整 timeout。
- 后续做准确率和成本统计。

面试里不要只说“我加了重试”，还要说“我把重试次数和耗时做成了可观测数据”。

## 七、配置入口

后台默认配置：

```bash
TEACHX_TOOL_MAX_ATTEMPTS=3
TEACHX_TOOL_TIMEOUT_SECONDS=30
TEACHX_TOOL_RETRY_BASE_DELAY_MS=200
TEACHX_TOOL_RETRY_MAX_DELAY_MS=2000
```

配置之间是分层关系：

```text
工具自己的 ToolPolicy
→ 覆盖 Registry 默认值
→ 最终得到本次执行的有效政策
```

如果工具把 `max_attempts` 设为 `1`，即使 Registry 默认是 `3`，也不会重试。

## 八、自动测试如何验证重试

测试不能真的等待几秒，所以测试中把退避设置为 0：

```python
ToolExecutionDefaults(
    max_attempts=3,
    timeout_seconds=1.0,
    retry_base_delay_seconds=0,
    retry_max_delay_seconds=0,
)
```

目前覆盖：

1. 第一次临时失败，第二次成功。
2. 永久错误只执行一次。
3. 临时错误连续失败，达到最大次数后返回稳定错误码。
4. 工具超时后按政策重试。
5. 未知工具返回 `unknown_tool`。
6. Runtime 把尝试次数放进 `tool_result` 事件。
7. 知识库 SQLite locked 时自动重试。

运行：

```bash

```

## 九、面试问答

### 1. 为什么要重试？

因为部分失败是临时的，例如网络抖动、数据库锁竞争、外部服务短暂不可用。有限重试可以提升成功率，但不能掩盖永久错误。

### 2. 哪些错误可以重试？

只重试明确标记为临时错误或超时的异常。参数错误、权限错误、业务校验失败和未知代码错误默认不重试。

### 3. 为什么不直接 `except Exception: retry`？

因为它会重试不可恢复错误，可能产生重复副作用、放大故障和无限延迟。还会隐藏真正的代码 Bug。

### 4. 什么是指数退避？

每次失败后按指数增加等待时间，例如 200 ms、400 ms、800 ms，并设置最大等待时间。它给下游系统恢复时间，同时降低请求压力。

### 5. 为什么需要 jitter？

大量客户端如果使用完全相同的退避时间，会在同一时刻再次请求，形成重试风暴。随机抖动可以打散重试时间。

### 6. 超时和重试是什么关系？

超时决定单次执行最多等多久，重试决定超时或临时失败后是否再次尝试。两者必须共同受最大尝试次数约束。

### 7. 什么是幂等？

同一个操作执行一次和执行多次，最终业务效果相同。重试有副作用工具前必须有幂等保护，否则可能发送两封邮件、创建两个订单或重复扣费。

### 8. 当前保证 exactly-once 吗？

工具调用现在通过幂等键和 `tool_executions` 执行记录保证“相同业务请求只产生一次副作用”（见第十一章）。重试本身仍然只是有限尝试；exactly-once 是重试和幂等记录配合的结果，不是重试单独能保证的。

### 9. 为什么把重试放在 ToolRegistry？

因为重试、超时和错误分类是所有工具共享的策略。放在 Registry 可以统一行为、减少重复代码，并让 Agent Loop 保持简单。

### 10. 如何测试等待和超时？

把退避设为 0 避免测试变慢；使用一个很短的 timeout 和一个故意 sleep 的假工具测试超时；用可控失败次数的假工具测试重试成功和重试耗尽。

### 11. 应该记录哪些指标？

至少记录 attempt_count、retry_count、retryable、error_code、timed_out 和 duration_ms。生产环境还可以统计重试率、P95 延迟和按工具分类的失败率。

### 12. 重试和熔断有什么区别？

重试处理单次请求的临时失败；熔断在下游持续故障时暂时阻止请求，避免继续放大故障和浪费资源。

### 13. 为什么未知异常默认不重试？

未知异常可能是代码 Bug、数据损坏或权限问题。没有确认可恢复性和幂等性前，盲目重试不安全。

### 14. 为什么不用一个大 timeout 包住整个回合？

单工具 timeout 能定位具体失败点，并允许工具级政策。整回合 timeout 仍然需要，但它属于更上层的 deadline 控制。

### 15. 这个设计对应什么工程原则？

对应深模块和横切关注点集中：外部接口很小，重试、超时、错误分类和元数据都在内部完成；调用方不重复实现这些逻辑。

## 十、当前边界

- 还没有添加 jitter。
- 还没有熔断器和全局并发限制。
- 还没有统一的完整 trace，只先提供工具级 metadata。
- 未知异常默认不重试，这是为了安全，不代表它是永久错误。
- 幂等保护已经上线，但“短暂等待后仍未完成的重复请求”只会得到
  `tool_execution_in_progress`，不会一直阻塞等待。
- 原始工具参数不落库，只保存 SHA-256 指纹；参数脱敏属于 E3。

E2 已经加入幂等保护，设计见下一章。

## 十一、E2：工具执行幂等保护

### 11.1 三种语义：at-least-once、at-most-once、exactly-once

E1 完成后，工具执行仍然是 at-least-once：临时失败会重试，极端情况下一次业务请求可能
执行工具多次。对只读工具（计算器、知识检索）这没有问题；对有副作用的工具（发邮件、
建日历、提交作业、扣费）就是真实事故。

| 语义 | 含义 | 风险 |
| --- | --- | --- |
| at-least-once | 至少执行一次，可能多次 | 重复副作用 |
| at-most-once | 至多执行一次，可能一次都不执行 | 丢失执行 |
| exactly-once | 业务效果恰好一次 | 只能靠“标识请求 + 持久化记录 + 原子写入”近似达成 |

E2 的做法是：给每次工具调用一个稳定身份，执行前先原子地“登记”，后来的重复请求读到
登记记录就直接返回第一次的结果。分布式系统里这叫 deduplication（去重）。

### 11.2 幂等键必须稳定，且按用户隔离

幂等键由六个字段组成：

```text
user_id + session_id + turn_id + call_id + tool_name + arguments_hash
→ SHA-256 → idempotency_key
```

为什么每个字段都不可少：

- `call_id` 是模型给的调用编号，重试同一个请求时不变，是去重的核心。
- `turn_id` 区分同一会话里的不同回合。用户下一回合再问同一个问题，参数 hash 相同，
  但这是新的业务请求，必须重新执行。
- `tool_name` 防止两个不同工具的参数巧合一致。
- `user_id` 保证用户隔离。没有它，两个用户用相同参数会互相“借到”对方的执行结果。
- `session_id` 让排查问题时能定位回话。

代码位置：

```text
backend/src/teachx/runtime/tool_executions.py
```

两个必须避开的坑：

- 不要用随机 UUID 当幂等键——每次重试都会生成新键，永远去不了重。
- 不要只用 `call_id`——不同回合、不同用户可能出现相同的 `call_id`。

### 11.3 为什么用 canonical JSON + SHA-256

模型给的参数是 JSON 对象，键的顺序不保证稳定：

```python
{"a": 1, "b": 2}   # 和
{"b": 2, "a": 1}   # 是同一份参数
```

所以先做 canonical JSON：`sort_keys=True` 排序键、`separators=(",", ":")` 去掉多余空格、
`ensure_ascii=False` 统一中文处理，再整体做 SHA-256：

```python
json.dumps(arguments, ensure_ascii=False, sort_keys=True, separators=(",", ":"), default=str)
```

用 SHA-256 还有一个安全考虑：数据库里只存 hash，不存原始参数。这样日志和数据库
泄露时也不会直接暴露用户提交的内容，也为 E3 的参数脱敏留好了边界。

### 11.4 tool_executions 表与状态机

```text
idempotency_key TEXT PRIMARY KEY   ← 唯一约束就是并发控制
user_id / session_id / turn_id / call_id / tool_name / arguments_hash
read_only INTEGER
status TEXT            ← running / completed / failed
result_content TEXT    ← 第一次执行的结果，重放时原样返回
result_metadata TEXT   ← 包含 sources 等业务元数据
error_content TEXT
attempt_count INTEGER
created_at / updated_at REAL
```

执行流程：

```text
计算幂等键
→ INSERT OR IGNORE 一条 status = running 的记录
→ 插入成功：我是第一个请求，执行工具，结束后写终态
→ 插入冲突：读已有记录
   → completed：直接重放保存的结果（deduplicated = true）
   → failed 且不可重试（永久错误）：重放保存的失败终态
   → failed 且可重试（临时错误耗尽）：接管记录，重新执行
   → running：短暂轮询等待；等不到就返回 tool_execution_in_progress
```

“接管”用一条条件 UPDATE 完成，天然原子：

```sql
UPDATE tool_executions SET status = 'running', updated_at = ?
WHERE idempotency_key = ? AND status = 'running' AND updated_at <= ?   -- stale
```

为什么临时失败要允许重新执行，而永久失败要重放？因为临时失败（比如重试耗尽的网络
抖动）不是业务结论，把失败缓存住会让模型之后的合法重试永远拿到旧的失败；永久失败
（参数错误）重跑一万次结果都一样，重放又快又省。

### 11.5 为什么数据库唯一约束比内存字典可靠

- **进程重启不丢失**。内存字典重启后为空，重启瞬间的重复请求会再次执行副作用。
- **跨进程有效**。多个 uvicorn worker 或多台机器共享同一个 SQLite/数据库时，内存字典
  各自为政，只有共享存储的唯一约束是全局闸门。
- **原子性由存储引擎保证**。`INSERT OR IGNORE` 撞唯一键的判定和写入在同一条语句里，
  不存在“先查后写”的检查窗口（check-then-act 竞态）。

### 11.6 配置

```bash
TEACHX_TOOL_IDEMPOTENCY_ENABLED=true     # 关闭后退回 E1 行为
TEACHX_TOOL_EXECUTION_STALE_SECONDS=300  # running 超过该秒数视为可接管
```

stale 接管是崩溃恢复的最后手段：进程在“登记之后、写终态之前”崩溃时，记录会永远停在
`running`。超过 stale 时间后，新的重复请求可以接管重新执行。前提是确认旧执行进程
确实不会再写入——单机 SQLite 场景里，进程已死即可确认；多机部署时这个时间要大于
最大执行时长加时钟误差。

### 11.7 重复请求在事件里长什么样

`tool_result` 事件在 E1 字段基础上新增：

```json
{
  "deduplicated": true,
  "replayed": true,
  "execution_status": "completed",
  "idempotency_key_hash": "9d2b92ebd5a5c616"
}
```

- `deduplicated`：这次调用命中了已有执行记录。
- `replayed`：返回的内容来自数据库重放，而不是刚执行的工具。
- 重放会原样保留第一次的 `sources`、`success` 和业务 metadata，模型不会察觉差别。

backend/tests/test_tool_idempotency.py

10 个测试覆盖：

1. 第一次调用正常执行并写入执行记录。
2. 相同调用重放原结果，底层工具只执行一次，sources 保留。
3. 永久失败终态被重放，不重新执行工具。
4. 相同参数在不同 `turn_id` / `call_id` 下不会被误去重。
5. 不同用户相同参数不共享执行记录。
6. 并发重复请求只有一个获得执行权。
7. AgentRuntime 的 `tool_result` 事件携带 dedup 元数据。
8. 旧库迁移后 `tool_executions` 表自动创建。
9. 可重试失败允许接管重新执行，而不是缓存失败。
10. 没有 `turn_id` 的直接调用不启用幂等（兼容 E1 行为）。

## 十二、E2 幂等面试问答

### 16. exactly-once 是怎么“达成”的？

严格说分布式系统里做不到字面意义的 exactly-once 执行；工程上做的是 exactly-once
**效果**：每个业务请求有稳定标识，执行结果持久化，重复请求重放已保存的结果而不是
再次执行。TeachX 用幂等键 + `tool_executions` 唯一约束实现。

### 17. 为什么幂等键必须包含 user_id？

如果两个用户用相同参数调用相同工具，没有 user_id 时第二个用户会直接读到第一个用户的
执行结果——既是数据泄露，也是错误结果。身份必须参与键的计算。

### 18. 为什么用数据库唯一约束而不是内存字典？

内存字典在进程重启后丢失、在多进程/多机部署下不共享，而且“先查后写”存在竞态窗口。
数据库唯一键是共享的、持久的，`INSERT OR IGNORE` 的冲突判定是原子的。SQLite 单机
场景下唯一键加原子插入就够，不需要分布式锁。

### 19. 如果工具执行成功，但写终态失败怎么办？

这是 exactly-once 方案的固有缺口：副作用已发生，但记录还停在 `running`。后果是后续
重复请求要么短暂等待后拿到 `tool_execution_in_progress`，要么超过 stale 时间后接管
重执行——副作用可能发生两次。工程上的缓解手段：终态写入做成幂等更新（天然如此，
UPDATE 按 key 覆盖）、把“工具内副作用 + 记录”尽量放进同一个事务边界、stale 秒数
大于最大执行时长。面试时主动承认这个缺口比声称完美更能加分。

### 20. running 状态的记录卡死了怎么办？

`TEACHX_TOOL_EXECUTION_STALE_SECONDS`（默认 300 秒）之后，记录被视为可恢复：新的
重复请求用条件 UPDATE 接管它并重新执行。接管的前提是旧执行确实不会再写入，所以
stale 时间必须大于工具最大执行时长。

### 21. 为什么重放时要保留原来的 sources 和 metadata？

重放的对象是模型和前端，它们只关心“这次工具调用的结果”。如果重放丢掉 sources，
引用事件就消失了；丢掉业务 metadata，下游统计就断了。重放只允许追加去重标记，
不允许篡改业务结果。

### 22. 幂等和重试是什么关系？

重试回答“失败了要不要再来一次”，幂等回答“再来一次安不安全”。只有先有幂等保护，
对有副作用工具的重试才是安全的。这就是 E1 之前项目明知有重试风险仍把未知异常默认
不重试的原因。

### 23. 这套方案如何扩展到多机部署？

把 SQLite 换成 PostgreSQL，表结构和键计算逻辑不变；`INSERT OR IGNORE` 换成
`INSERT ... ON CONFLICT DO NOTHING`。幂等键的生成是纯函数，任何机器算出来的键一致，
所以多机共享同一张执行记录表即可，不需要引入分布式锁。

## 十三、E3：敏感工具参数脱敏

### 13.1 为什么要脱敏

`tool_call` 事件会被持久化到助手消息里，回显在前端工具轨迹中；执行记录会写入
`tool_executions` 表。OWASP LLM Top 10 把"敏感信息泄露"（Sensitive Information
Disclosure）列为大模型应用的主要风险之一：一旦未来加入带密钥、密码或个人身份的
工具（例如调用外部服务的 API Key），这些值就会明文躺在数据库和浏览器里。

E3 的做法是**让工具自己声明哪些参数名是敏感的**，执行层统一打码：

```python
class SendEmailTool(BaseTool):
    policy = ToolPolicy(
        read_only=False,
        sensitive_arguments=("api_key", "password"),
    )
```

### 13.2 打码发生在哪里

```text
tool_call 事件参数      → 打码（api_key: "***"）
tool_executions 表      → 只存参数 SHA-256 指纹（E2 已天然满足）
工具结果 metadata       → 与敏感参数同名的字段一并打码（防御性兜底）
发给模型的原始参数       → 不打码（模型需要真值才能执行工具）
工具内部收到的参数       → 不打码（否则工具无法工作）
幂等键                  → 用原始参数计算（脱敏规则变化不影响去重）
```

打码后的形态是固定占位符 `***`，保留字段名、只隐藏值——这样前端和日志仍然能看到
"这个调用带了哪些参数"，只是看不到值。

### 13.3 边界与责任

- 只做**顶层字段名精确匹配**，不做嵌套结构猜测。误脱敏会破坏业务数据，显式声明
  优于自动猜测。
- 如果工具把 secret 写进了**结果正文**（`result_content`），执行层无法安全自动
  打码——无法区分业务文本和密钥。这要靠工具的代码评审：声明了敏感参数的工具，
  不允许把参数值拼进返回内容。
- 现有 `calculator` 和 `knowledge_search` 没有敏感参数，行为完全不变。

### 13.4 配置与验证

```bash
TEACHX_TOOL_REDACTION_ENABLED=true   # 关闭后退回不脱敏行为
```

测试在 `backend/tests/test_tool_redaction.py`（7 个），覆盖：声明字段被打码、
未声明字段原样通过、开关可关、未知工具原样返回、结果 metadata 同名字段兜底、
幂等键不受影响、运行时事件打码但模型和工具收到原始值。

真实验证（运行时脚本，带敏感参数的演示工具走完整 Agent 回合）：

```text
tool_call 事件 arguments: {"to": "stu@example.com", "api_key": "***"}
tool_result 事件 metadata.api_key: ***
事件流中出现明文密钥: False
持久化消息+执行记录中出现明文密钥: False
```

## 十四、E3 参数脱敏面试问答

### 24. 为什么脱敏不能影响幂等键？

幂等键用**原始参数**的 SHA-256 计算。如果用脱敏后的值计算，两个问题会同时出现：
`api_key=sk-a` 和 `api_key=sk-b` 两个不同请求会被误判成同一个（都变成 `***`）；
反过来，脱敏规则一改（比如从 `***` 改成 `[redacted]`），所有历史键都变了，去重
全部失效。原则：**执行身份用真值，可观测表面用脱敏值**，两者必须分离。

### 25. 为什么发给模型的原始参数不能脱敏？

模型是工具的调用方，它必须拿到真值才能构造有效的工具调用——脱敏后的 `***` 发给
执行层，工具要么失败要么执行出错误结果。脱敏的目标是"可观测表面"（事件、数据库、
日志），不是执行链路。这也是"脱敏层放在事件组装处，而不是参数入口处"的原因。

### 26. 为什么只做顶层字段名精确匹配？

嵌套结构里哪个字段敏感因工具而异（同样是 `config`，一个工具放密钥、一个放阈值），
自动递归猜测要么漏掉要么误杀。误脱敏的代价是破坏业务数据且很难发现。显式声明 +
顶层精确匹配是第一版最可验证的边界；嵌套脱敏等具体工具出现真实需求时，让该工具
自己声明点路径更可靠。

### 27. 如果工具把 secret 写进了结果正文怎么办？

执行层不自动打码正文——无法区分"这是密钥"和"这是用户正好需要的一段文本"。
防御手段是分层的：工具声明了敏感参数后，代码评审必须检查它的返回内容不拼接参数值；
未来可以加内容扫描器（正则识别已知密钥格式，如 `sk-` 开头的 Key）作为第二道网，
发现即告警并轮换密钥。面试时主动说"正文脱敏是未解问题"比假装已解决更加分。

### 28. 这和 OWASP LLM Top 10 是什么关系？

E3 对应其中的 Sensitive Information Disclosure（敏感信息泄露）。同一份清单里的
Excessive Agency（过度代理）对应后续 E9 的工具权限分级和人类审批，Unbounded
Consumption（无限制消耗）对应已完成的日预算和输出上限。做每个稳定性功能时都能
对应到一份公开安全清单，说明设计不是拍脑袋。
