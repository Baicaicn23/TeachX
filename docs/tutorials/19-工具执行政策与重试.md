# 19：工具执行政策与重试

> 本章适合第一次接触工具调用、重试和超时机制的读者。读完后，你应该能够解释：
> 为什么不能所有错误都重试，什么是有限重试，以及生产 Agent 如何观察一次工具调用。

## 这一章解决什么问题

之前的工具调用只有一条简单路径：

```text
模型请求工具
→ ToolRegistry.execute()
→ 工具执行一次
→ 成功或失败
```

这会产生几个问题：

- 数据库短暂锁住时，本来重试一次就能成功，却直接失败。
- 参数写错时，如果无脑重试，只是重复浪费三次。
- 工具一直不返回时，整个 Agent 回合会一直卡住。
- 前端只知道“失败”，不知道尝试了几次、是否超时、错误是否可重试。

E1 把工具执行升级为：

```text
模型请求工具
→ 读取工具自己的执行政策
→ 判断错误是临时还是永久
→ 临时错误执行有限退避重试
→ 每次执行都有超时上限
→ 返回尝试次数、重试次数、耗时和错误码
```

## 用户场景

用户提问时，知识库正在被另一个写入操作短暂占用。SQLite 返回：

```text
database is locked
```

这不是用户的问题，也不是模型参数错误，而是临时资源冲突。

TeachX 的处理结果是：

```text
第 1 次：数据库 locked，失败
→ 等待退避时间
第 2 次：检索成功
→ Agent 继续回答，用户甚至不需要知道发生过重试
```

另一个场景是计算器参数无效：

```text
expression = "__import__('os').system('whoami')"
```

这是永久性参数错误，重试三次仍然会失败，所以必须立即停止。

## 一、错误必须分类

“重试”最危险的实现方式是：

```python
except Exception:
    retry()
```

它会把参数错误、权限错误、代码 Bug、数据库锁定和网络抖动全部当成同一种问题。

TeachX 现在分成三类：

| 类型 | 含义 | 是否重试 | 例子 |
| --- | --- | --- | --- |
| `ToolError` | 永久性业务或参数错误 | 否 | 表达式非法、参数缺失 |
| `ToolTransientError` | 临时失败，重复请求有机会成功 | 是 | 数据库 locked、外部服务短暂不可用 |
| `ToolTimeoutError` | 单次执行超过时间上限 | 是，完成次数受限 | 知识库查询长时间无响应 |

代码位置：

```text
backend/src/teachx/runtime/tools.py
```

核心接口：

```python
class ToolError(ValueError):
    code = "tool_error"


class ToolTransientError(RuntimeError):
    code = "tool_transient_error"


class ToolTimeoutError(ToolTransientError):
    code = "tool_timeout"
```

面试里可以用一句话解释：

> 重试策略的前提不是“失败了”，而是“这个失败是否具有恢复可能，并且重复执行是否安全”。

## 二、工具自己声明执行政策

不同工具不应该共用同一套策略。

计算器是纯函数，结果确定，没有网络和数据库，不需要重试；知识库搜索依赖 SQLite，存在短暂锁竞争。

因此新增 `ToolPolicy`：

```python
@dataclass(frozen=True, slots=True)
class ToolPolicy:
    read_only: bool = True
    max_attempts: int | None = None
    timeout_seconds: float | None = None
    retry_base_delay_seconds: float | None = None
    retry_max_delay_seconds: float | None = None
```

`None` 表示继承 `ToolRegistry` 的默认值。

当前工具政策：

```python
# CalculatorTool
policy = ToolPolicy(read_only=True, max_attempts=1, timeout_seconds=2.0)

# KnowledgeSearchTool
policy = ToolPolicy(read_only=True, max_attempts=3, timeout_seconds=10.0)
```

为什么 `read_only` 暂时还没直接参与执行？

它是为后续能力准备的：

- E2 根据是否有副作用决定是否允许重复执行。
- E4 只读工具可以并发的有上限执行，有副作用工具保持串行。

提前把“工具的语义”放在统一接口上，避免以后每个工具单独判断。

## 三、重试放在 ToolRegistry，而不是每个工具里

每个工具如果自己写：

```text
for attempt in range(3)
try/except
sleep
metadata
```

会产生大量重复代码，也很难保证所有工具行为一致。

TeachX 把重试放到 `ToolRegistry.execute()`：

```text
AgentRuntime
→ ToolRegistry.execute()
→ 解析有效政策
→ 循环调用具体工具
→ 返回统一 ToolResult
```

这是一种“深模块”设计：

- 外部接口仍然只有一个 `execute()`。
- 重试、超时、退避、错误分类和元数据都在内部完成。
- Agent Loop 不需要知道工具实现用了数据库还是 HTTP。

面试可以这样回答：

> 我把横切关注点放在 ToolRegistry 这一层，而不是散落到每个工具。调用方只需要知道一次工具执行的结果，不需要理解重试策略。

## 四、有限重试与指数退避

当前退避公式：

```python
delay_seconds = min(
    retry_max_delay_seconds,
    retry_base_delay_seconds * (2 ** (attempt_count - 1)),
)
```

默认配置：

```text
第 1 次失败后等待 200 ms
第 2 次失败后等待 400 ms
第 3 次失败后等待 800 ms
最多等待 2000 ms
```

为什么不能固定 10 ms 连续重试？

- 外部服务可能正在恢复。
- 立刻重试只会继续打满资源。
- 多个请求同时重试会造成“重试风暴”。

生产环境通常还会加入 jitter，也就是随机抖动：

```text
200 ms + random(0 ~ 100 ms)
```

随机化可以避免大量客户端在同一个时间点同时重试。

当前 TeachX 使用确定性退避，方便测试；后续可以在不改变 `ToolRegistry` 接口的情况下加入 jitter。

## 五、超时不是失败重试的替代品

超时解决的是：

```text
工具一直不返回，Agent 回合不能无限等待
```

当前使用：

```python
await asyncio.wait_for(
    tool.execute(context=context, **arguments),
    timeout=policy["timeout_seconds"],
)
```

如果超时，会产生：

```text
error_code = tool_timeout
timed_out = true
retryable = true
```

要注意：`asyncio.wait_for` 会取消等待中的协程，但它无法强制停止一个正在阻塞线程的同步函数。

所以工具内部应优先使用：

- `async` 数据库客户端。
- `httpx.AsyncClient`。
- 异步文件或网络调用。

否则 timeout 可能只是让调用方放弃等待，后台线程仍继续运行。

## 六、尝试次数和耗时必须可观察

成功后，工具返回的 metadata 会包含：

```json
{
  "attempt_count": 2,
  "retry_count": 1,
  "retry_delays_ms": [200],
  "duration_ms": 231.42,
  "read_only": true,
  "max_attempts": 3,
  "timeout_seconds": 10
}
```

失败时还会包含：

```json
{
  "error_code": "tool_timeout",
  "retryable": true,
  "timed_out": true,
  "attempt_count": 3,
  "retry_count": 2
}
```

这些字段会进入 `tool_result` 事件，并持久化在助手消息中。

前端工具轨迹会显示：

```text
attempts  2 (1 retries)
duration  231.42 ms
```

为什么这些字段重要？

- 排查失败到底发生在哪一层。
- 评估工具延迟和重试率。
- 判断是否需要调整 timeout。
- 后续做准确率和成本统计。

面试里不要只说“我加了重试”，还要说“我把重试次数和耗时做成了可观测数据”。

## 七、配置入口

后台默认配置：

```bash
TEACHX_TOOL_MAX_ATTEMPTS=3
TEACHX_TOOL_TIMEOUT_SECONDS=30
TEACHX_TOOL_RETRY_BASE_DELAY_MS=200
TEACHX_TOOL_RETRY_MAX_DELAY_MS=2000
```

配置之间是分层关系：

```text
工具自己的 ToolPolicy
→ 覆盖 Registry 默认值
→ 最终得到本次执行的有效政策
```

如果工具把 `max_attempts` 设为 `1`，即使 Registry 默认是 `3`，也不会重试。

## 八、自动测试如何验证重试

测试不能真的等待几秒，所以测试中把退避设置为 0：

```python
ToolExecutionDefaults(
    max_attempts=3,
    timeout_seconds=1.0,
    retry_base_delay_seconds=0,
    retry_max_delay_seconds=0,
)
```

目前覆盖：

1. 第一次临时失败，第二次成功。
2. 永久错误只执行一次。
3. 临时错误连续失败，达到最大次数后返回稳定错误码。
4. 工具超时后按政策重试。
5. 未知工具返回 `unknown_tool`。
6. Runtime 把尝试次数放进 `tool_result` 事件。
7. 知识库 SQLite locked 时自动重试。

运行：

```bash
./scripts/check.sh
```

当前结果：

```text
45 passed
typecheck passed
```

## 九、面试问答

### 1. 为什么要重试？

因为部分失败是临时的，例如网络抖动、数据库锁竞争、外部服务短暂不可用。有限重试可以提升成功率，但不能掩盖永久错误。

### 2. 哪些错误可以重试？

只重试明确标记为临时错误或超时的异常。参数错误、权限错误、业务校验失败和未知代码错误默认不重试。

### 3. 为什么不直接 `except Exception: retry`？

因为它会重试不可恢复错误，可能产生重复副作用、放大故障和无限延迟。还会隐藏真正的代码 Bug。

### 4. 什么是指数退避？

每次失败后按指数增加等待时间，例如 200 ms、400 ms、800 ms，并设置最大等待时间。它给下游系统恢复时间，同时降低请求压力。

### 5. 为什么需要 jitter？

大量客户端如果使用完全相同的退避时间，会在同一时刻再次请求，形成重试风暴。随机抖动可以打散重试时间。

### 6. 超时和重试是什么关系？

超时决定单次执行最多等多久，重试决定超时或临时失败后是否再次尝试。两者必须共同受最大尝试次数约束。

### 7. 什么是幂等？

同一个操作执行一次和执行多次，最终业务效果相同。重试有副作用工具前必须有幂等保护，否则可能发送两封邮件、创建两个订单或重复扣费。

### 8. 当前保证 exactly-once 吗？

没有，也不能只靠重试保证。当前是 at-least-once 风格的有限重试；E2 会通过幂等键和执行记录避免重复副作用。

### 9. 为什么把重试放在 ToolRegistry？

因为重试、超时和错误分类是所有工具共享的策略。放在 Registry 可以统一行为、减少重复代码，并让 Agent Loop 保持简单。

### 10. 如何测试等待和超时？

把退避设为 0 避免测试变慢；使用一个很短的 timeout 和一个故意 sleep 的假工具测试超时；用可控失败次数的假工具测试重试成功和重试耗尽。

### 11. 应该记录哪些指标？

至少记录 attempt_count、retry_count、retryable、error_code、timed_out 和 duration_ms。生产环境还可以统计重试率、P95 延迟和按工具分类的失败率。

### 12. 重试和熔断有什么区别？

重试处理单次请求的临时失败；熔断在下游持续故障时暂时阻止请求，避免继续放大故障和浪费资源。

### 13. 为什么未知异常默认不重试？

未知异常可能是代码 Bug、数据损坏或权限问题。没有确认可恢复性和幂等性前，盲目重试不安全。

### 14. 为什么不用一个大 timeout 包住整个回合？

单工具 timeout 能定位具体失败点，并允许工具级政策。整回合 timeout 仍然需要，但它属于更上层的 deadline 控制。

### 15. 这个设计对应什么工程原则？

对应深模块和横切关注点集中：外部接口很小，重试、超时、错误分类和元数据都在内部完成；调用方不重复实现这些逻辑。

## 十、当前边界

- 还没有添加 jitter。
- 还没有熔断器和全局并发限制。
- 还没有幂等键和重复执行记录。
- 还没有统一的完整 trace，只先提供工具级 metadata。
- 未知异常默认不重试，这是为了安全，不代表它是永久错误。

下一步 E2 会加入幂等保护：

```text
turn_id + call_id + tool_name + arguments_hash
→ 唯一 idempotency key
→ 重复执行返回第一次保存的结果
```
