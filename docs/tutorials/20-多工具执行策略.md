# 20：多工具执行策略与稳定顺序

> 本章适合已经读完[教程 19](19-工具执行政策与重试.md)（工具政策、重试、幂等、脱敏）
> 的读者。读完后，你应该能够解释：为什么只读工具可以并发而副作用工具必须串行，
> 结果顺序如何保证稳定，以及并发度为什么要有上限。

## 这一章解决什么问题

模型在一轮推理里可能一次请求多个工具调用，例如同时查两个概念再提交总结。
之前 TeachX 的处理是完全串行：

```text
调用 lookup(线性代数)   等待 0.5 秒
调用 lookup(概率论)     再等 0.5 秒
调用 submit(...)        再等 0.3 秒
```

三个互相独立的只读查询排队执行，用户白等了一半时间。但把所有工具都并发执行
也不行：如果 submit（提交作业、扣费、发邮件）和别的工具同时跑，顺序不可控，
副作用可能交错发生。

E4 的答案是**按风险分组**：

```text
连续的只读调用 → 组成一批，有上限地并发执行
有副作用(或未知)的调用 → 单独一批，严格串行
所有结果 → 按模型调用顺序返回，永不乱序
```

## 用户场景

用户提问"对比线性代数和概率论在机器学习里的作用，然后总结提交"。
模型一轮返回 4 个工具调用：

```text
call-1  lookup(线性代数)      只读
call-2  lookup(概率论)        只读
call-3  submit(总结)          有副作用
call-4  lookup(课程表)        只读
```

E4 的执行计划是三批：

```text
批 1: [call-1, call-2]  并发执行(最多 2 个同时)
批 2: [call-3]          单独串行,期间没有其他工具运行
批 3: [call-4]          单独执行(它是新一批只读,但批次里只有它一个)
```

事件流仍然是模型给的顺序：call-1 → call-2 → call-3 → call-4。

## 一、怎么判断一个工具能不能并发

判断依据是工具在 `ToolPolicy` 里声明的 `read_only`（E1 就埋好的字段）：

```python
class LookupTool(BaseTool):
    policy = ToolPolicy(read_only=True, ...)    # 可以进并发批

class SubmitTool(BaseTool):
    policy = ToolPolicy(read_only=False, ...)   # 必须单独串行
```

运行时通过 `ToolRegistry.is_read_only(name)` 查询。两个刻意的设计：

- **未知工具返回 `False`**（按有副作用处理）。执行一个没注册的工具本来就只会
  失败，把它放进并发批没有任何收益，保守处理永远不会错。
- **声明来自工具作者，不是调用方猜测**。只有写工具的人知道它有没有副作用，
  Agent Loop 不做启发式判断。

## 二、分批算法

代码在 `backend/src/teachx/runtime/engine.py` 的 `_plan_tool_batches()`：

```text
按模型调用顺序扫描
→ 当前是只读工具:加入正在积累的只读批
→ 当前是副作用/未知工具:先结算只读批,再把它自己作为单元素批
→ 扫描结束:结算剩余的只读批
```

要点：

- **只合并"连续"的只读调用**。`[读, 读, 副, 读]` 分成 `[读,读] [副] [读]` 三批，
  而不是把两个不相邻的读凑到一起——那会改变副作用工具的相对位置。
- 批的顺序就是模型调用顺序，后面对结果的组装不需要重排。

## 三、并发执行与保序

`_execute_tool_batch()` 用 `asyncio.Semaphore` 限制并发上限，
`asyncio.gather` 并发执行整批：

```python
semaphore = asyncio.Semaphore(self.max_tool_concurrency)

async def run(call):
    async with semaphore:
        return await self.tools.execute(...)

return list(await asyncio.gather(*(run(call) for call in batch)))
```

两个关键性质：

1. **`gather` 的返回顺序等于传入顺序**，与谁先完成无关。call-2 即使先执行完，
   它的结果也排在 call-1 后面。这就是"稳定顺序"的实现——不是靠等待或重排，
   而是选了一个自带保序语义的原语。
2. **信号量限制同时在跑的工具数**。批里有 10 个只读调用、并发上限是 4 时，
   任何时刻最多 4 个在执行，其余在信号量前排队。上限保护下游资源
   （数据库连接、外部 API 配额），避免并发本身把系统打挂。

`tool_call` 事件增加了两个可观察字段：

```json
{ "batch_size": 2, "parallel": true }
```

前端工具轨迹可以看到"这两个调用是一批并发的"。

## 四、为什么副作用工具必须单独串行

三个理由：

1. **顺序语义**。提交作业前必须先完成两个查询——如果副作用和查询并发，
   模型调用里的先后关系就被破坏了。
2. **故障隔离**。副作用工具失败的影响是真实世界级别的（重复扣费、错误提交），
   让它独占执行窗口，出问题时现场干净、容易排查。
3. **E2 幂等的前提配合**。幂等保护解决"重复请求"，串行解决"同时发生"。
   两个不同参数的副作用调用即使幂等键不同、各自只执行一次，同时执行仍可能
   在业务层产生交错（例如两个库存扣减并发读改写）。串行是最简单的正确性保证。

## 五、为什么并发度要有上限

无上限并发（一把梭 `gather`）在调用少时看起来没问题，但：

- 模型一轮最多可能请求十几个调用，下游 SQLite 写锁或外部 API 会被打满。
- 重试是在每个工具内部发生的（E1），并发 × 重试相乘会放大故障。
- 排队成本很低（协程挂起几乎无开销），而打挂下游的成本很高。

默认 `TEACHX_TOOL_MAX_CONCURRENCY=4`，设为 `1` 即完全退回串行
（行为与 E4 之前完全一致，这就是回滚开关）。

## 六、和 E1~E3 怎么组合

E4 是建立在前三项之上的分层设计，每层各管一件事：

| 层 | 管什么 | 在并发批里怎么起作用 |
| --- | --- | --- |
| E1 重试/超时 | 单次调用的失败恢复 | 每个并发中的工具独立重试,互不影响 |
| E2 幂等 | 重复请求去重 | 并发的不同调用 call_id 不同、键不同;同键并发只有一个执行 |
| E3 脱敏 | 可观测表面安全 | 事件里的参数照样打码,与并发无关 |
| E4 分批 | 调用之间的编排 | 只读并发、副作用串行、顺序稳定 |

这也是为什么路线图坚持 E2 → E3 → E4 的顺序：没有幂等，并发重试会重复执行副作用；
没有脱敏，并发的事件流会更快地泄露敏感参数。

## 九、当前边界

- 分批只看模型调用顺序里的**连续性**，不做全局只读重排（这是刻意的,见第二节）。
- 没有跨回合的工具级缓存——两个回合里相同参数的只读查询会各自执行
  （幂等键包含 turn_id,不会命中同一记录）。
- 并发批里的一个工具失败不影响同批其他工具（gather 不设 return_exceptions,
  单个失败会变成失败的 ToolResult 返回,批次正常收尾）。
- 前端工具轨迹已能看到 batch_size/parallel 字段,但没有"并发动机画"之类的可视化。

## 十、面试问答

### 1. 为什么不把所有工具调用都并发执行？

因为有副作用的工具并发会破坏模型调用里的顺序语义,还可能在业务层产生交错
（两个扣减并发读改写）。只读工具之间没有这些风险,所以只有它们进并发批。
按风险分组比"全并发"和"全串行"都更合理。

### 2. 结果顺序是怎么保证的？

`asyncio.gather` 的返回值顺序等于传入顺序,与完成顺序无关。执行层不做任何
重排,事件组装和 tool 消息追加都按模型调用顺序遍历结果。测试里专门用一个
"慢的在前、快的在后"的用例证明:完成顺序乱了,返回顺序也不乱。

### 3. 为什么用信号量而不是直接开协程池?

要控制的资源是"同时在执行的工具数",信号量精确表达这个语义,而且可以和
gather 保序组合。协程池(如 ProcessPoolExecutor)针对的是 CPU 密集任务,
工具调用是 IO 密集,asyncio 协程 + 信号量已经足够,引入线程/进程池反而
复杂化错误处理和超时控制。

### 4. 并发上限设多少合适?

默认 4。依据是:下游是 SQLite(写锁单写者)和外部 API(有限流),并发收益
在 2~4 之间最明显,再高只会把压力转移给下游。这个值应该根据真实下游能力调,
并且设为 1 可以随时退回全串行——配置即回滚开关。

### 5. 一个并发工具失败了会怎样?

失败在 ToolRegistry.execute 内部被转换成 `success=False` 的 ToolResult
（E1 的设计）,gather 正常收到它,批次其余工具不受影响,失败结果照样按序
发给模型,模型可以决定重试或绕过。异常不会炸掉整批——这是"错误是数据,
不是中断"的原则。

### 6. 为什么只合并"连续"的只读调用?

如果把 `[读A, 副作用, 读B]` 重排成 `[读A, 读B] [副作用]`,副作用工具的
相对位置就变了——模型明确要求它发生在读A之后。保序约束下,能安全并发的
只有相邻的只读片段。全局重排换取的加速不值得付出语义风险。

### 7. 并发下幂等和脱敏还成立吗?

成立。幂等键包含 call_id,并发的不同调用键不同,各自独立登记;相同键并发
到达时(E2 已测)只有一个能插入 running 记录。脱敏发生在事件组装处,
每个工具的事件独立打码,与执行方式无关。组合验证见第八节。

### 8. 如果工具内部有线程或不安全的状态,并发会出问题吗?

会。并发批的前提是工具自己是协程安全的:不用阻塞调用占住事件循环、
共享状态要加锁或用不可变数据。这就是教程 19 说的"工具内部应优先使用
async 客户端"。运行时不检查这一点,靠工具作者遵守——policy 声明本身
就是"我确认这个工具可以安全并发"的契约。

### 9. 这套设计对应什么通用模式?

生产者-消费者的有界并发 + 按语义分组的调度策略。在更宏观的分布式语境里,
它是"只读副本并发、写主库串行"思想的工具级缩影。面试时可以把它讲成
一致性 vs 延迟的 trade-off:副作用串行牺牲延迟换顺序正确性。

### 10. 怎么证明并发真的发生了?

测试用共享计数器记录峰值并发数(peak = 2),不是靠总耗时推断——耗时受
机器负载影响,峰值计数是确定性证据。运行时验证同样输出峰值。这就是
"可观察性优先"的思路:每个机制都要有能直接观测的证据。
