# 23:回合 trace——失败去哪了,一眼看到

> 本章适合读完[教程 22](22-RAG检索评测.md)的读者。读完后,你应该能回答面试里
> Observability 方向的必问问题:**"你的 Agent 出了问题,你怎么定位是模型、检索、
> 提示词还是工具的锅?"**

## 这一章解决什么问题

用户说"回答不对",你面对的可能是完全不同的四种故障:

```text
模型层:供应商限流、流中断、超时
检索层:知识库里根本没检索到资料
工具层:计算器参数错、知识库被锁重试三次
编排层:回合超时、工具调用轮数耗尽
```

没有 trace 时,排查 = 打开数据库翻原始事件 JSON,肉眼比对几十个字段。
E6b 交付的是一把**放大镜**:`turn_trace` 命令读一回合已持久化的事件,
输出一份诊断报告,把每个异常定位到上面五层之一。

## 一、为什么不需要引入 OpenTelemetry

教科书答案会说"上 OpenTelemetry,定义 span 语义约定"。本项目刻意没这么做,
理由值得面试讲:

**事件流本身就是 trace。** 每个回合的事件已经有:序号(`seq`)、时间戳、
`turn_id`、逐层元数据(工具的尝试次数/错误码、模型的轮次、错误分类),并且
持久化在消息里。缺的不是数据,是**把数据变成判断**的工具。

所以学习版的 trace = 一个纯函数分析器:

```text
回合事件列表 → analyze_turn_events() → 诊断报告(状态/时长/轮数/工具/发现)
            → render_trace()        → 给人读的文本
```

没有 agent、没有 collector、没有新中间件——但"失败能定位到层"这个核心价值
已经拿到了。将来真要接 OpenTelemetry,事件流的字段直接映射 span 属性即可。

## 二、责任层怎么定

分析器的核心是一张**错误码 → 责任层**映射表(`turn_trace.py`):

| 错误码 | 责任层 |
| --- | --- |
| `provider_timeout` / `rate_limited` / `stream_interrupted` 等 | 模型层 |
| `turn_timeout` / `max_rounds_exceeded` / `runtime_error` | 编排层 |
| `daily_budget_exceeded` | 费用层 |
| `tool_execution_in_progress` | 工具层 |
| `knowledge_search` 的失败 | 检索层 |
| 其他工具的失败 | 工具层 |
| 没见过的错误码 | **未知层(不猜)** |

两条设计规则:

1. **映射基于 E5 统一过的稳定错误码**——这就是为什么先做 E5 再做 trace:
   错误码不稳定,映射表就得天天改。
2. **未知错误码归"未知层",不做猜测。** 宁可告诉用户"这是新问题,需要人看",
   也不能把锅甩给错误的层——错误的定位比没有定位更误导。

除了错误,分析器还报告**警告**(还没失败但值得注意):

- `tool_retried`:工具发生过重试(临时性不稳定的信号)
- `empty_retrieval`:knowledge_search 检索到 0 条资料
- `tool_context_truncated`:工具结果太长被截断后才传给模型
- `turn_not_finalized`:事件流里没有 done(连接中断或进程退出)

## 三、用一次

先让本地跑出一些回合,然后(backend 目录下):

```bash
# 看某个会话的最后一回合
uv run python -m teachx.runtime.turn_trace --session <会话id>

# 指定某条助手消息
uv run python -m teachx.runtime.turn_trace --session <会话id> --message <消息id>

# 分析别的数据库(比如复现问题时导出的)
uv run python -m teachx.runtime.turn_trace --db /path/to/db --session <会话id>
```

健康回合的输出:

```text
回合 trace  turn=54691f...  状态=completed  时长=0.0s  轮数=2  工具调用=1
工具 knowledge_search(c1) 成功 尝试 1 次 0ms
未发现异常
```

有问题的回合:

```text
回合 trace  turn=54691f...  状态=completed  时长=0.0s  轮数=2  工具调用=1
[warning] 检索层  empty_retrieval  knowledge_search(c1) 没有检索到任何资料
工具 knowledge_search(c1) 成功 尝试 1 次 0ms
```

一眼结论:回答质量差不是模型的锅——是检索层根本没找到资料。

## 五、当前边界

- 分析器读的是**已持久化**的事件;正在进行中的回合要等它结束(或断掉)才能看。
- 警告规则是白名单式的,新的异常模式要手动加规则——这是刻意的:分析规则
  本身就是代码,每条都要有测试,不搞自动魔咒。
- 没有 trace 采样率、没有跨会话统计(比如"最近 100 回合的检索空结果率")——
  那是下一步"聚合"的事,当前先解决"单回合定位"。
- 回答质量(忠实度/引用正确性)不在 trace 范围内,属于评测(E6 剩余部分)。

## 六、面试问答

### 1. 你的 Agent 出了问题,你怎么定位?

每个回合的完整事件流本来就持久化了(E1~E5 给事件加了错误码、尝试次数、
去重标记等元数据)。我写了 `turn_trace` 分析器:输入一回合事件,输出诊断
报告,按稳定错误码把异常归到模型/检索/工具/编排/费用五层。一条命令就能
回答"这次失败是谁的锅"。

### 2. 为什么不用 OpenTelemetry?

两个原因:一是事件流已经具备 trace 需要的全部要素(序号、时间戳、层级
元数据、持久化),缺的只是把它变成判断的分析器,一个纯函数就够;二是
这是学习项目,引入 collector/agent 的运维复杂度换不来对应的认知收益。
真要上 OTel,事件字段可以平移成 span 属性——接口留好了。

### 3. 错误怎么归层?没见过的错误码怎么办?

一张静态映射表:供应商类错误码 → 模型层;`turn_timeout`/`max_rounds_exceeded`
→ 编排层;`knowledge_search` 的失败 → 检索层;其他工具 → 工具层。没见过的
错误码归"未知层"并且不猜——错误的定位比没有定位更危险,宁可让人看。

### 4. 错误和警告的区别?

错误 = 这一回合已经失败了或某次工具调用失败了,一定对应一个稳定错误码;
警告 = 没失败但不健康(发生过重试、检索为空、结果被截断、没有 done 事件)。
警告的价值是发现"还没坏但快坏了"的趋势,比如重试警告变多通常预示下游
不稳定。

### 5. `empty_retrieval` 为什么是警告而不是错误?

工具调用本身成功了(没抛异常),回合也正常结束——只是没检索到资料。
但用户会觉得"回答没用",从用户视角这就是故障。把它定为检索层警告,
排查时第一眼就能看到:问题不在模型,在知识库覆盖或检索质量。

### 6. trace 和评测(教程 22)是什么关系?

评测回答"整体好不好"(聚合指标,跑固定考卷);trace 回答"这一次为什么坏"
(单回合诊断,读真实事件)。一个管均值,一个管个案。工程上先有 trace 的
数据基础(带元数据的事件),评测和监控都从它长出来。

### 7. 怎么保证分析器自己是对的?

分析器是纯函数,每条归层规则和警告规则都有对应的手工构造事件用例
(9 个测试);还有一个端到端测试:跑真实 AgentRuntime 回合,把数据库里
持久化的事件直接喂给分析器,验证真实事件形状和测试构造的一致。

### 8. 如果要做"最近 100 回合的检索空结果率"这种统计,还差什么?

差聚合层:遍历会话的消息事件逐回合调用 `analyze_turn_events`,把发现
按层/代码计数。分析器已经返回结构化 dict,聚合只是循环累加——这正是
先做纯函数分析器的原因:单回合逻辑和聚合逻辑解耦,后者随时能加。
