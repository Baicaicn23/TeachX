# 05：向量检索与混合排序

## 先理解两种检索方式

假设知识库里有：

```text
工具结果返回后，Agent Loop 会继续调用模型。
```

用户输入可能有两种情况。

### 情况一：关键词基本相同

```text
用户：工具结果返回后会发生什么？
```

这种问题适合“关键词检索”。TeachX 使用 SQLite FTS5 完成。

### 情况二：表达方式不同

```text
用户：执行函数以后还会继续推理吗？
```

句子里没有“工具结果返回”这些原词，但意思接近。  
这种问题适合“向量检索”，因为它比较的是语义方向，而不是要求文字完全相同。

## 什么是 Embedding

Embedding 会把一句话转换成一组数字：

```text
"Agent 调用工具"
→ [0.12, -0.08, 0.31, ...]
```

这组数字叫“向量”。

语义相近的句子，在向量空间中的方向通常更接近。我们可以通过余弦相似度比较两个
向量的方向是否接近。

## 为什么不能只用向量检索

真实产品中，两种情况都存在：

- 用户输入明确术语时，关键词检索非常准确。
- 用户换一种说法时，向量检索更有效。

因此生产系统通常采用 Hybrid Search，也就是混合检索：

```text
关键词检索 + 向量检索 → 合并排序 → 返回结果
```

## TeachX 的向量模块

相关文件：

```text
backend/src/teachx/knowledge/embeddings.py
```

接口只有一个小方法：

```python
class BaseEmbeddingProvider:
    async def embed(self, texts: list[str]) -> list[list[float]]:
        ...
```

它有两条实现：

- `MockEmbeddingProvider`：本地 Hash 向量，不需要 API Key。
- `OpenAIEmbeddingProvider`：调用 OpenAI 兼容 Embeddings API。

Mock 向量不是生产级语义模型。它主要帮助测试：

- 数据库存储是否正确。
- 向量查询是否执行。
- FTS 和向量结果能否融合。
- 页面在没有 API Key 时是否可以演示。

## 向量怎样保存

SQLite 本身不提供向量类型，因此 TeachX 暂时把向量保存为 JSON：

```sql
CREATE TABLE knowledge_chunk_vectors (
    chunk_id INTEGER PRIMARY KEY,
    model TEXT NOT NULL,
    dimensions INTEGER NOT NULL,
    vector TEXT NOT NULL,
    created_at REAL NOT NULL
);
```

数据量不大时，Python 可以读取向量并直接计算余弦相似度：

```python
dot = sum(a * b for a, b in zip(left, right))
similarity = dot / (left_norm * right_norm)
```

未来文档量变大后，可以替换为 FAISS、pgvector 或 Qdrant，而不改变上层接口。

## 为什么需要记录模型名称

不同 Embedding 模型生成的维度不同，向量空间也不同。  
同一个查询不能拿 `text-embedding-3-small` 的向量去比较另一个模型生成的向量。

因此每条向量都记录：

```text
model
dimensions
vector
```

检索时只使用当前模型对应的向量。

## FTS 和向量如何合并

TeachX 没有直接把 BM25 和余弦相似度相加，因为它们的数值范围不同。

这里使用 RRF，全称 Reciprocal Rank Fusion：

```text
score = 1 / (60 + 排名)
```

如果某个文本块：

- 在 FTS 中排第 1
- 在向量检索中排第 2

它会得到两个分数并相加。  
这样融合的是“排名”，不是不同检索器不可比较的原始分值。

```text
backend/src/teachx/knowledge/service.py
```

## 已有文档如何补建向量

知识库可能先通过 FTS5 创建，后来才配置 Embedding 模型。  
普通搜索无法找到没有向量的数据。

因此提供：

```python
await service.reindex_embeddings("课程资料")
```

它只会处理当前模型还没有向量的文本块，不会重复计算所有内容。

对应 API：

```text
POST /api/knowledge-bases/{kb_name}/reindex
```

## 如何启用真实 Embedding

复制后端环境配置：

```bash
cp backend/.env.example backend/.env
```

设置：

```bash
TEACHX_EMBEDDING_PROVIDER=openai
TEACHX_EMBEDDING_MODEL=text-embedding-3-small
OPENAI_API_KEY=your-api-key
OPENAI_BASE_URL=https://api.openai.com/v1
```

然后重启后端。已有知识库可以调用 reindex 接口补建向量。

## 为什么没有使用 LangChain

当前混合检索只需要：

- 一个 Embedding 接口。
- 一个 SQLite 向量表。
- 一个余弦相似度函数。
- 一个 RRF 合并函数。

这些代码规模很小，而且和 TeachX 的 `SearchHit`、引用事件、知识库删除逻辑紧密相关。
直接手写可以保持接口简单，也避免为了检索引入完整 Agent 框架。

LangChain 或其他向量框架可以在未来需要多后端适配时局部引入，但要放在
`KnowledgeService` 后面，不要接管 Agent Loop。

## 当前局限

- 向量保存在 SQLite，适合个人知识库，不适合千万级数据。
- Mock 向量只有词项重合效果，不具备真正的语义理解。
- 当前 RRF 使用固定权重，后续可以增加检索器权重和 rerank。
- 没有处理 Embedding API 限流、重试和并发控制。
- 图片型 PDF 仍然需要 OCR。
