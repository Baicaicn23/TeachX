# TeachX 文档写作指南

> 适用对象：TeachX 的开发者、维护者和后续 Codex Agent。
>
> 默认读者：学过一点 Python 或 JavaScript，但对 Web、Agent、数据库和部署不熟悉的
> 学习者。写文档时不要假设读者已经知道项目背景。

这份指南参考了以下公开资料，并结合 TeachX 现有教程做了取舍：

- [Diátaxis：教程、操作指南、参考和解释](https://diataxis.fr/)
- [Write the Docs：软件文档入门指南](https://www.writethedocs.org/guide/writing/beginners-guide-to-docs/)
- [The Good Docs Project：文档模板库](https://www.thegooddocsproject.dev/template)
- [Microsoft Writing Style Guide：清晰、直接的写作原则](https://learn.microsoft.com/en-us/style-guide/top-10-tips-style-voice)

## 最重要的一条：文档是完成标准

每次任务结束前都要做一次“文档判定”：

```text
代码或设计完成
→ 判断是否改变用户行为、接口、配置、架构或排障方式
→ 更新对应文档
→ 检查 README、教程、roadmap、HANDOFF 是否同步
→ 给出验证证据
```

不是每次代码修改都要新增一篇教程，但每次任务都必须明确处理文档。

| 本次变化 | 至少要更新 |
| --- | --- |
| 新功能、新页面、新工作流 | 中文教程；README 功能说明；roadmap；HANDOFF 状态 |
| 新配置、新命令、安装方式变化 | 对应教程；`.env.example`；README 快速开始 |
| API、数据库表、稳定架构变化 | 架构文档；相关的数据或接口参考；HANDOFF |
| Bug 修复改变用户行为 | 相关教程或排障说明；如果用户能看到差异，更新 README/roadmap |
| 纯重构、测试、注释、格式调整 | 不强行新增教程，但要检查现有文档是否失真，并在交付说明中写明文档判断 |

## 先决定写哪一种文档

Diátaxis 把技术文档分为四类。TeachX 采用它的核心思想，不再把“教程”“说明”
“参考”和“排障”混成一锅。

| 类型 | 读者现在在做什么 | 应该怎么写 |
| --- | --- | --- |
| 教程 Tutorial | 学习一项能力 | 带读者走一条固定路线，保证能成功，解释每一步为什么 |
| 操作指南 How-to | 完成一个具体任务 | 直接给前置条件、步骤、验证结果和常见错误 |
| 参考 Reference | 查准确事实 | 参数、接口、表格、字段和限制，少讲背景 |
| 解释 Explanation | 理解为什么这样设计 | 讲概念、取舍、架构和数据流，不要求读者马上操作 |

TeachX 的 `docs/tutorials/` 主要是“教程 + 解释”的教学文章。它们可以使用类比，
但最终必须落在真实代码、真实命令和可验证结果上。

## 面向基础一般的读者

### 先给结论，再给细节

标题下先用一两句话回答：

```text
这一章解决什么问题？
读者读完后会得到什么？
```

不要一上来就列类名、函数名和文件路径。先让读者知道这些东西为什么存在。

### 每个术语第一次出现时都要解释

推荐写法：

```text
Embedding（向量表示）就是把一段文字转换成一串数字。
```

不推荐：

```text
调用 Embedding API 后写入 vector store。
```

后者对熟悉的人很快，但对第一次接触 RAG 的读者没有入口。

### 一次只讲一个概念

- 一个段落只承担一个主要意思。
- 长句子拆成短句。
- 先讲输入和输出，再讲内部实现。
- 代码可以逐段解释“数据从哪里来、交给谁”，不要逐行翻译语法。
- 使用“你”来直接说明读者要做什么。

### 给出可观察的结果

只要让读者运行命令、点击页面或修改配置，就说明预期结果：

```bash
./scripts/check.sh
```

预期看到：

```text
All checks passed!
45 passed
```

如果结果可能因环境不同而变化，明确说明差异和检查方式。

### 不回避错误

初学者最需要知道“失败时看哪里”。教程至少要包含：

- 常见错误现象。
- 最可能的原因。
- 一条优先尝试的解决步骤。
- 超出本教程范围时应该继续读哪份文档。

### 使用友好的语言

避免“显然”“只需要”“很简单”“大家都知道”这类说法。它们不会让文章更短，
只会让遇到困难的读者觉得自己跟不上。

## 推荐的新功能教程结构

创建新教程时，按下面的顺序写。可以根据功能删减小节，但不要省略“验证”和“边界”。

```text
1. 标题：本章解决什么问题
2. 用户场景：谁在什么情况下使用
3. 完成后的结果：读者能看到什么
4. 前置知识：只列真正需要的内容
5. 操作步骤：编号，每步都有预期结果
6. 核心原理：数据如何流动，为什么这样设计
7. 失败与排障：常见错误和处理方式
8. 自动测试与验证：命令、测试数量和浏览器/API 证据
9. 当前边界：现在还不能做什么
10. 面试问答：为什么这样设计、替代方案和常见追问
11. 自测题：检查读者是否真的理解
```

可以直接复制下面的骨架：

```markdown
# 19：这项功能解决什么问题

> 本章适合第一次接触……的读者。读完后，你将能够……

## 为什么需要它

先描述真实用户场景，再说明没有这项功能时会遇到什么问题。

## 最终结果

读者完成操作后，应该看到什么页面、事件、数据或命令输出。

## 前置条件

- 需要安装什么。
- 需要准备什么文件。
- 不需要准备什么，避免读者误以为缺少东西。

## 操作步骤

### 1. 第一步做什么

运行命令或操作页面，然后说明预期结果和关键原理。

## 它是怎么工作的

用一个数据流或三到五步流程解释核心机制，不要把整份源码逐行抄一遍。

## 常见错误

| 现象 | 原因 | 处理方式 |
| --- | --- | --- |
| 页面提示…… | 配置缺少…… | 修改……后重启 |

## 验证

列出自动测试、API 或浏览器验证的真实结果。

## 当前边界

明确哪些场景已经支持，哪些还没有实现。

## 面试问答

至少准备 8 个问题，覆盖：

- 为什么需要这项技术。
- 当前实现是怎么工作的。
- 为什么不用另一种方案。
- 失败时会发生什么。
- 并发、性能或安全方面有什么取舍。
- 如何测试和观察这项能力。

## 自测题

1. 用自己的话说……
2. 如果把……改成……，会发生什么？
```

## 写法对照

| 避免 | 推荐 |
| --- | --- |
| “实现了 `UsageService`” | “系统会记录每次模型调用用了多少 token” |
| “在 reducer 中 dispatch” | “收到事件后，前端把用量更新到当前回答下方” |
| “配置 max_tokens” | “`max_tokens` 用来限制模型最多生成多少输出 token” |
| “测试通过” | “运行 `./scripts/check.sh`，结果为 `45 passed`” |
| 大段代码后没有解释 | 先说明代码解决的问题，再只解释关键数据流 |

技术名词、命令、文件名、API 字段保留英文，解释文字使用中文。这样既容易读，
也方便搜索。

## 文档之间的分工

| 文件 | 回答的问题 |
| --- | --- |
| `README.md` | 这个项目是什么，怎么快速运行，现在能做什么 |
| `docs/README.md` | 所有文档的导航地图 |
| `docs/tutorials/*` | 这个能力为什么存在，代码如何工作，新手怎么理解 |
| `docs/参考/*` | 查准确事实：架构、API、数据库表、配置 |
| `docs/规划/开发路线图.md` | 项目已经做到哪里，下一步做什么 |
| `docs/交接文档.md` | 下一个 Agent 接手时需要知道什么 |
| 本文件的"README 维护规范"一章 | README 的专门结构和更新标准 |

同一个事实只保留一个权威来源。其他文档可以链接过去，不要复制三份后分别过期。

## 交付前检查

- [ ] 第一段说明了用户价值和完成后的结果。
- [ ] 术语第一次出现时有解释。
- [ ] 每个命令都有预期输出或成功标志。
- [ ] 说明了至少一个常见错误和排查入口。
- [ ] 包含至少 8 个面试问答，讲清设计动机、替代方案和取舍。
- [ ] 代码名称、配置名和实际代码一致。
- [ ] 说明了当前边界，没有把计划写成已完成。
- [ ] 测试、构建或浏览器验证有真实证据。
- [ ] README、roadmap、HANDOFF 中受影响的部分已同步。
- [ ] 没有 API Key、Auth Secret、真实账号或机器专属绝对路径。
- [ ] 基础一般的读者可以顺着文章独立完成一次验证。

## 判断文档是否合格的三个问题

1. 一个第一次接触项目的人，能不能说出这项功能解决什么问题？
2. 他能不能按步骤操作，并知道什么结果才算成功？
3. 失败时，他能不能先自己判断问题在哪，而不是只能重新来问？

三个问题都能回答“可以”，这篇文档才算完成。

## README 维护规范

> 本章由原 `docs/readme-guide.md` 合并而来。它只负责 `README.md` 的结构和维护。
> 这套标准基于三个高信号开源项目 README 的结构分析：
> [Dify](https://github.com/langgenius/dify)（产品平台型）、
> [Open WebUI](https://github.com/open-webui/open-webui)（Web 应用型）、
> [Generative AI for Beginners](https://github.com/microsoft/generative-ai-for-beginners)（教学型），
> 只借鉴结构和表达原则，不照搬文字。

### 优秀 README 的三条经验

- **Dify：产品价值优先。** 访客应该在看到实现细节之前先明白产品是什么。
- **Open WebUI：先展示，再安装。** 用可见的演示证明产品可用，然后扫清首次运行的障碍。
- **教学型项目：定义读者。** 说明读完能做什么，而不是仓库里有什么文件。

### 首屏只放五样东西

1. 项目名和视觉标识。
2. 一句话说明项目是什么。
3. 少量真实的状态/技术徽章。
4. 用平实语言描述的当前阶段。
5. 指向演示、截图或快速开始的路径。

### 推荐章节顺序

2026-10-04 重构后的现行结构（居中 Hero + emoji 分节 + 次要内容折叠）：

```text
居中 Hero（横幅、一句话定位、徽章、页内导航）
两句话简介（DeepTutor 归属 + 选型依据链接）
技术亮点（表格:图标 | 能力 | 一句话说明）
当前边界（折叠在 <details> 里,诚实但不上首屏）
快速开始（含 Mock 变体;真实模型配置折叠）
质量与验证（check.sh + 评测命令 + trace 命令）
项目结构（代码树）
文档与教程（分组链接,突出面试问答特色）
开发路线（一行一站的紧凑表,标注项目定位）
维护者入口
上游关系与许可（折叠在 <details> 里）
```

### 写作规则

- 先讲用户得到什么，再讲类名和实现。
- 每个功能声明都必须可运行，或明确标注为计划中。
- 状态语言要诚实，不把计划写成已完成。
- 高级配置放 `docs/`，README 保持轻量。
- 徽章只保留有意义的信号（状态、版本、CI、许可证）。
- 不写无法演示的营销话术。
- 不出现 API Key、私有地址或本机路径。
- 深入内容用链接，不把 README 写成手册。
- 保留上游归属和许可证信息。

### 更新时机

大型功能落地后必须更新 README：新用户可见能力、新模型供应商/数据库/部署方式、
安装或启动命令变化、影响贡献者的公开 API 或架构变化、发布或作品集里程碑。

小修、重构、纯测试改动、文案微调、不影响使用的依赖升级**不需要**更新 README。

### 更新前检查表

- [ ] 里程碑可运行、可演示，测试和构建通过。
- [ ] 当前状态和开发路线与代码一致。
- [ ] 快速开始命令验证过。
- [ ] 新能力按用户结果描述。
- [ ] 无 Secret、无机器专属路径。
- [ ] 上游归属和许可证准确。

### 语言规则

- 主 `README.md` 使用中文；Python 包名、API、命令、协议字段和技术专有名词保留英文。
- 如果未来需要英文版本，使用独立的 `README.en.md`，不要让同一文件承担两种语言。
